토리가 비티와 사탕통 놀이를 해요.

## 🔍 원리 들여다보기 <a id="why"></a>

### 비유 → 정식 용어

| 비유 | 정식 용어 | 이 레슨에서 보는 값 |
|---|---|---|
| 사탕통 장부 | TRC-20 컨트랙트(Nile USDT) | `TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf` |
| 내 사탕 수 칸 | `balanceOf(owner)` | `19589.654444 USDT` |
| 허락증 | `approve(spender, amount)` 트랜잭션 | 선택자 `095ea7b3` + spender + amount |
| "몇 알까지" 칸 | `allowance(owner, spender)` | `0 USDT (허락 없음)` |
| 숫자 칸이 빈(전부) 허락증 | 무제한 approve = 2^256-1 | `ffff…ffff` (64자리 f) |
| 허락증 0으로 고치기 | `approve(spender, 0)` | 취소도 트랜잭션 1건 |

### 실험 1: 출력에서 한 줄 찾기

`npm run l09`를 실행하고 `[2]` 단계에서 이 줄을 찾습니다.

```
  워드 2 (amount): 00000000000000000000000000000000000000000000000000000000002dc6c0 → 3000000 = 3 USDT
```

`2dc6c0`은 16진수입니다. 2×16^5 + 13×16^4 + 12×16^3 + 6×16^2 + 12×16 + 0 = 3,000,000. decimals가 6이므로 10^6으로 나누면 3 USDT입니다. 그 아래 "무제한 허락증의 워드 2" 줄에 있는 `ffff…ffff`(64자리 f)는 2^256-1, 즉 "전부"입니다. 허락증의 숫자 칸은 이렇게 16진수 64자리로 적힙니다.

### 실험 2: 환경변수 바꿔 보기

```bash
AMOUNT_USDT=0.5 npm run l09
```

`[2]`의 워드 2가 `…07a120`(= 500,000)으로, `[1]`의 "이번에 허락하려는 금액"이 `0.5 USDT = 최소 단위 500000`으로 바뀝니다. 이번엔 `SPENDER=TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf npm run l09`처럼 spender를 다른 주소로 바꿔 보세요. `[1]`의 allowance는 (owner, spender) 쌍마다 따로 적히므로 값이 달라질 수 있습니다. 어느 실험에서도 전송은 일어나지 않습니다.

### 숫자로 확인하기

- approve 리허설의 `energy_used`는 **22688**. 에너지 가격 100 sun이므로 스테이킹 에너지가 없으면 2.2688 TRX가 소각됩니다. 허락증을 쓰는 데도 연료(규칙 4)가 듭니다.
- calldata는 68바이트 = 선택자 4 + 주소 칸 32 + 금액 칸 32. 주소는 20바이트지만 32바이트 칸에 앞을 0으로 채워 넣습니다.
- 무제한 = 2^256-1 ≈ 1.16×10^77. 이 저장소의 guard는 이 값의 절반 이상이면 모두 "무제한"으로 보고 막습니다.

### 왜 그렇게 설계했을까?

왜 토큰을 그냥 보내지 않고 "허락 → 나중에 spender가 꺼내 감(transferFrom)"이라는 두 단계를 둘까요? 자판기(컨트랙트)는 스스로 내 사탕통에 손을 넣을 수 없습니다. 내가 먼저 "이 자판기가 내 사탕통에서 N알까지 꺼내도 됨"이라고 적어 둬야, 자판기가 물건을 줄 때 사탕을 가져갈 수 있습니다.

편리하지만, 그 N이 "전부"이면 자판기(또는 자판기의 구멍을 찾은 사람)가 전부를 가져갈 수 있습니다. 상한 N이 곧 위험의 크기입니다. 그래서 규칙 9는 "필요한 만큼만"과 "다 쓰면 0으로"를 한 세트로 묶습니다.

### 비유의 한계 (한 줄)

허락증은 돌려받으면 끝이지만, allowance는 spender가 다 쓰지 않는 한 저절로 줄지 않으며 0으로 다시 써야(approve(0), 트랜잭션 1건) 끝납니다.

```bash
npm run l09
# 환경변수: MNEMONIC(없으면 데모), SPENDER(기본 index 1 주소), AMOUNT_USDT(기본 3), SEND_TX, COUNTDOWN, LEVEL, SHOW_SECRETS
```

Nile 읽기 → 리허설 → 미서명 빌드까지가 기본입니다(약 1.8초). 데모 니모닉이면 `[6]`의 guard 에서 멈추고 exit 0. 아래는 핵심 줄만 인용했습니다 — **전체 출력은 [expected-output.txt](./expected-output.txt) 참고.**

### [1/6] balanceOf / allowance — 잔고 칸과 허락 칸은 다르다

```
  balanceOf(owner): 19589.654444 USDT (최소 단위 19589654444)
  allowance(owner, spender): 0 USDT (허락 없음)
```

`allowance`는 `(owner, spender)` 쌍마다 따로 저장되는 상한입니다. 잔고와 다른 칸이며, 잔고보다 큰 값도 저장은 됩니다(잔고 검사는 `transferFrom` 때 — 리허설 `triggerConstantContract`로 확인).

### [2/6] approve calldata 만들고 되읽기

```
  선택자 (앞 4바이트): 0x095ea7b3 = keccak256("approve(address,uint256)")[:4] MATCH
  워드 1 (spender): 000000000000000000000000b6e708a39781c96bd399c7657780ff9fe9f052a8 → TSeJkUh4Qv67VNFwY8LaAxERygNdy6NQZK
  무제한 허락증의 워드 2: ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff → 2^256-1
```

`ethers.Interface(TRC20_ABI).encodeFunctionData('approve', [0x주소, amountRaw])` 가 그대로 68바이트 calldata(선택자 4 + 주소 32 + 금액 32)입니다. hex 만 보여 주는 앱에서는 앞 8글자가 함수, 다음 64글자의 뒤 40글자가 spender, 마지막 64글자가 금액이며(금액 칸 읽기는 실험 1), 마지막 64글자가 모두 `f` 이면 무제한입니다.

### [3/6]·[4/6] 리허설과 미서명 봉투

```
  energy_used: 22688 → 스테이킹 에너지가 없으면 22688 × 100 sun = 2.2688 TRX 소각
  constant_result[0]: 0000000000000000…00000001 (true)
  contract.type: TriggerSmartContract
  fee_limit: 30000000 sun = 30 TRX
  ethers calldata 와 비교: MATCH (트론 data = EVM calldata)
  signature: 없음 — 아직 도장을 안 찍었습니다
```

허락증을 쓰는 데도 에너지가 듭니다. 이 컨트랙트의 `approve`는 32바이트 `…01`(true)을 돌려주지만 `transfer`는 bool 을 돌려주지 않아 32바이트 0 이 나옵니다(레슨 10). 봉투의 `data`는 [2]의 calldata 에서 `0x`만 뗀 것, `fee_limit`은 태울 수 있는 sun 상한이고, `txID`·`expiration`(60초)은 실행마다 달라집니다.

### [5/6] guard — 무제한 approve 차단

```
  이번 금액 3 USDT (3000000): 통과 (필요한 만큼만)
  무제한 금액 (2^256-1): ⚠️ 차단 대상 — SEND_TX 가 true 여도, 내 니모닉이어도 4번째 관문에서 막힙니다
```

guard는 관문(SEND_TX → 데모 니모닉 → 메인넷 host → 무제한 금액)을 순서대로 검사하므로 `SEND_TX=false`에서는 첫 관문 메시지가 나옵니다. 스크립트는 같은 기준(`approveAmount ≥ UNLIMITED / 2`)을 로컬에서도 계산해, SEND_TX 상태와 무관하게 "무제한은 차단 대상"임을 보여 줍니다.

### [6/6] 실제 approve → allowance → approve(0)

```js
await assertCanSend({ mnemonic, approveAmount: amountRaw, what: `USDT approve(${AMOUNT_USDT})` }); // 브로드캐스트 직전
// 통과하면: sign → sendRawTransaction → receipt 폴링 → allowance 재조회 → approve(0) → 폴링 → allowance
```

`SEND_TX=true` + 연습용 니모닉(.env)일 때만 approve → 확인 → approve(0) 까지 한 세트로 돌고, 두 번 모두 브로드캐스트 직전에 `assertCanSend`를 부릅니다. 기본값은 `🛑 미리보기 종료` 로 끝납니다. 실제 전송 출력(receipt 값)은 작성자가 SEND_TX=true 로 실행하지 않아 비어 있습니다(확인 필요).

### 트론 vs EVM 차이

| 항목 | 트론(TRC-20) | EVM(ERC-20) |
|---|---|---|
| 선택자 · calldata | `approve` = `095ea7b3`, `data`(0x 없는 hex)가 ethers 인코딩과 바이트 단위로 같음 | 같은 선택자, `0x` + hex |
| 주소 인코딩 | 32바이트 칸 뒤 20바이트 = T주소의 `41` 뺀 부분 | 32바이트 칸 뒤 20바이트 = 0x주소 |
| 수수료 상한 | `feeLimit`(sun) — 에너지 소각 상한 | `gasLimit` × `gasPrice` |
| 리허설 · 봉투 | `triggerConstantContract` → `energy_used`, 봉투는 `TriggerSmartContract` | `eth_call` / `estimateGas`, 일반 트랜잭션의 `to`+`data` |

### 함정 1개

`tronWeb.contract(...)`에는 `lib/tron.js`의 `TRC20_ABI`처럼 **JSON ABI 객체 배열**을 넘겨야 합니다. ethers식 문자열 ABI(`'function approve(address,uint256)'`)를 넘기면 예외 없이 조용히 `approve` 메서드가 없는 객체가 나옵니다. `ethers.Interface`는 같은 JSON 배열을 그대로 받으므로 ABI 하나로 조회와 인코딩을 다 하되, ethers 쪽 주소만 0x주소로 바꿉니다(`41` 떼고 `0x` 붙임).

### 도전

- 쉬움: `AMOUNT_USDT=0`으로 실행해 `[2]`의 워드 2와 `[5]`의 "이번 금액" 판정을 보고, `[3]`의 `energy_used`가 3 USDT일 때와 같은지 다른지 확인하세요.
- 어려움: `[7]` 단계를 추가해 `getContract(NILE.usdt).abi.entrys` 의 `Approval` 이벤트에서 indexed 필드(owner, spender)와 value 를 출력하고, 토픽 해시를 `TronWeb.sha3('Approval(address,address,uint256)')`로 계산해 맞춰 보세요(레슨 7 연결).

## 🏠 내 생활에서는 <a id="life"></a>

지갑 앱(TronLink 등)에서 DEX나 브릿지, 스테이킹 서비스를 처음 쓰면 "승인(Approve)" 팝업이 먼저 뜹니다. 토큰을 보내는 화면이 아닌데 수수료(TRX)가 드는 것이 특징입니다. 이것이 이 레슨의 `approve`이고, 그 서비스가 내 USDT를 "얼마까지" 꺼내 갈 수 있는지가 `allowance`입니다.

이 개념이 화면에서 보이는 자리 (앱·사이트마다 이름과 구성이 다를 수 있음, 확인 필요)

- 서비스를 처음 쓸 때 뜨는 "승인/Approve" 팝업 — 여기서 토큰·상대·금액 세 칸을 읽습니다.
- 팝업의 "무제한(Unlimited) / 사용자 지정" 선택 — 이번에 쓸 금액만 넣으세요.
- 팝업의 "데이터/Data" 칸 — `095ea7b3`로 시작하면 승인 요청입니다.
- 탐색기(Tronscan)의 승인 관리 화면 — 남아 있는 승인을 확인·취소할 수 있다고 알려져 있으나 화면은 직접 확인하세요(확인 필요).

다 쓴 뒤에는 그 화면에서 취소하거나, 같은 spender에게 0을 다시 승인하세요.

| 이런 요청이 오면 | 사기인가? | 이유 |
|---|---|---|
| 자주 쓰는 거래 서비스에서 "USDT 100 승인"을 요청하고, spender가 그 서비스의 컨트랙트 주소로 확인됨 | 아니오(금액 확인 후 승인) | 필요한 만큼의 허락증입니다. 다 쓰면 0으로 |
| "에어드랍 수령"이라며 승인 팝업이 뜨고 금액이 무제한, spender는 처음 보는 주소 | 예 | 내 토큰 전부를 꺼내 갈 허락증입니다. 규칙 9 |
| "토큰을 받으려면 승인이 필요합니다"라는 링크가 문자·DM으로 옴 | 예 | 받는 데는 승인이 필요 없습니다. 승인은 "꺼내 가도 됨"입니다 |

**사기 유형 1개: "수령용 승인" 피싱.** 에어드랍이나 환불을 준다며 승인 팝업을 띄웁니다. 승인은 받는 것과 상관없고, 상대에게 내 토큰을 꺼내 갈 권한을 주는 것입니다. 무제한으로 승인하면 지갑에 남은 USDT 전부가 나중에 한 번에 빠져나갈 수 있습니다. 사탕통 번호(컨트랙트 주소)와 spender 주소가 무엇인지 읽을 수 없으면 닫으세요.

**오늘 실천 습관 1개:** 승인 팝업이 뜨면 "어느 토큰, 누구에게(spender), 얼마까지" 세 칸을 소리 내어 읽으세요. 세 칸을 읽는 연습은 [허락증 판독기](../../playground/approve-decoder.html)에서 할 수 있습니다. 오늘 무언가를 승인하거나 취소할 필요는 없습니다.

> **금액 수정과 `approve 0` 은 수수료가 드는 실제 전송입니다.** 이 레슨의 리허설에서 approve 한 번이 `energy_used` 22688 → 100 sun/energy 기준 약 2.2688 TRX 소각으로 나왔습니다(위 💻 블록 참고). 금액을 이번에 쓸 만큼으로 고치는 것과, 서비스 사용이 끝난 뒤 승인을 0으로 돌려놓는 것은 둘 다 온체인 트랜잭션이므로 **급하게 하지 말고 여유 있을 때, 연료(TRX)를 확인한 뒤** 하세요. 이 코스 안에서는 아무것도 보내지 않고 화면만 봅니다.

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 9. 허락(approve)은 필요한 만큼만, 다 쓰면 0으로.**

**해야 할 것**
- ✅ 승인 금액을 이번에 쓸 만큼으로 직접 적는다.
- ✅ spender 주소가 내가 쓰려는 서비스의 컨트랙트인지 확인한다.
- ✅ 다 쓰면 같은 spender에게 0을 승인해 허락증을 끝낸다.

승인 팝업에서 읽는 순서: ① 어느 토큰 → ② 누구에게(spender) → ③ 얼마까지.

**절대 하지 말 것**
- ❌ "무제한(Unlimited)" 승인을 편하다고 고르지 않는다.
- ❌ "받으려면 승인하세요"라는 말에 승인하지 않는다. 받는 데는 승인이 필요 없다.
- ❌ 데이터 칸이 `095ea7b3…ffff…`인 요청을 읽지 않고 누르지 않는다.

## ✅ 확인하기 <a id="check"></a>

- **초등:** 여우 씨가 숫자 칸이 비어 있는 허락증을 내밀어요. 토리는 어떻게 해야 할까요? ① 친구니까 찍어 줘요 ② "몇 알까지"를 적어야 찍어요 ③ 반만 찍어요
- **중고등:** `approve(spender, 3000000)`을 보내도 `balanceOf(owner)`는 바뀌지 않습니다. 토큰이 실제로 나가는 순간은 어떤 함수가 실행될 때인지, 그 함수가 왜 allowance를 확인해야 하는지 두 문장으로 쓰세요.
- **개발자:** `AMOUNT_USDT=1 npm run l09`를 실행하면 `[2]`의 "워드 2 (amount)" 줄 끝 6글자는 무엇이고, `[5]`의 "이번 금액 … " 줄 판정은 무엇일까요?
- **일반인:** 처음 보는 사이트가 "에어드랍을 받으려면 USDT 승인이 필요합니다"라며 무제한 승인 팝업을 띄웠습니다. 승인해도 될까요?
