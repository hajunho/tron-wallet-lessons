## ✋ 손으로 해보기 <a id="hands"></a>

**활동: "될까 / 안 될까" 카드 판단 놀이** (20~25분, 4~10명. 자세한 진행은 [activity.md](./activity.md))

준비물: 상황 카드 12장, 판정 팻말 2개(초록 "될까" / 빨강 "안 될까"), 점검표 7칸 워크시트, 사탕상자 칩(종이 동그라미) 1인당 10개.

진행 5단계
1. **규칙 설명(3분)** — "리허설은 공짜예요. 하지만 리허설 없이 우체통에 넣었다가 넘어지면 우표(칩)를 내요." 각자 칩 10개를 받아요.
2. **카드 판정(10분)** — 카드를 한 장 읽고 "하나, 둘, 셋!"에 모두 팻말을 들어요. "안 될까"가 정답인데 "될까"를 든 사람은 칩 1개를 내요. "될까"가 정답인데 "안 될까"를 든 사람은 칩을 내지 않아요(안 보낸 건 손해가 아니에요).
3. **왜?(5분)** — 카드마다 한 명에게 "왜 안 될까?"를 물어요. 이유 칸(주소 / 사탕통 / 사탕상자 / 입장권 / 나라 / 상한)을 함께 확인해요.
4. **점검표 채우기(5분)** — 모둠별로 카드 1장을 골라 아래 7칸을 ✅/❌로 채워요. 하나라도 ❌면 "안 보낸다".
5. **정리(2분)** — 칩이 가장 많이 남은 사람이 "리허설 왕". 아래 발문으로 마무리해요.

점검표 7칸 워크시트 (카드 번호: ______)

| 번호 | 점검 칸 | 무엇을 보나요? | ✅ / ❌ |
|---|---|---|---|
| 1 | 주소 형식 | T로 시작하고, 나 자신이 아닌가 | |
| 2 | 수신자 활성화 | 받는 우편함이 열려 있나 (한 번도 받은 적 없으면 먼저 사탕상자를 조금 보내 열어요) | |
| 3 | 사탕상자(TRX) 잔고 | 상한(feeLimit)만큼 있나 | |
| 4 | 사탕통 잔고 ≥ 금액 | 보내려는 알 수보다 많나 | |
| 5 | 입장권(대역폭/에너지) | 입장권이 있거나, 없으면 태울 사탕상자가 있나 | |
| 6 | 나라(네트워크) | 상대가 말한 나라와 글자까지 같나 | |
| 7 | 상한(feeLimit) 설정 | 0이 아니고, 예상 × 1.2쯤인가 | |

**무장비 5분 버전 — 상황 읽고 손들기**
진행자가 상황을 읽으면 될 것 같으면 손을 위로, 안 될 것 같으면 손을 옆으로 뻗어요. 정답을 말한 뒤 한 명에게 "왜?"를 물어요. 아래 5개를 돌린 뒤 다 같이 외쳐요. "실패할 것 같으면 안 보낸다!"

- 받는 사람 주소가 T가 아니라 0x로 시작해요. (안 될까 — 나라가 달라요)
- 사탕통(USDT)은 100알인데 사탕상자(TRX)가 0이에요. (안 될까 — 입장권이 없어요)
- 사탕통 한 알을 보내는데 사탕상자도 입장권도 넉넉해요. (될까)
- 받는 사람이 나 자신이에요. (안 될까 — 자기한테는 못 보내요)
- 앱이 "실패할 것 같아요"라고 했는데 친구가 "그냥 보내"라고 해요. (안 될까 — 규칙 10)

**카드 예시 3장** (12장 전체는 [activity.md](./activity.md) 워크시트 2)

| 상황 | 판정 | 이유 |
|---|---|---|
| 리허설 기계가 "넘어졌어요"라고 했는데 친구가 "괜찮아, 보내"라고 해요 | 안 될까 | 규칙 10 |
| 입장권 상한(feeLimit)을 0으로 적었어요 | 안 될까 | 7번 상한 설정 |
| 예상 입장권보다 상한을 조금 넉넉히 적었어요 | 될까 | 상한 ≈ 예상 × 1.2 |

**손으로 한 걸음 더 — "리허설 성공"이 보장하지 않는 것**

리허설은 "지금 이 순간의 장부 상태"로만 계산합니다. 그래서 리허설이 성공이라도 아래 셋은 여전히 틀릴 수 있습니다. 카드 놀이 마지막에 이 셋을 소리 내어 확인하세요.

| 리허설이 못 잡아 주는 것 | 왜 | 사람이 확인할 방법 |
|---|---|---|
| 받는 주소를 잘못 골랐다 | 리허설은 "그 주소로 보낼 수 있나"만 봅니다. "그 주소가 내가 보내려던 사람인가"는 모릅니다 | 상대가 보낸 주소와 한 글자씩 대조(규칙 11) |
| 나라(네트워크)가 다르다 | 리허설은 지금 접속한 나라에서만 돌아갑니다 | 출금 화면 네트워크 칸을 상대 표기와 글자까지 맞춤(레슨 11) |
| 리허설 뒤에 장부가 바뀌었다 | 3초마다 새 장이 붙습니다. 그 사이 잔고·허락이 달라질 수 있습니다 | 보내기 직전에 한 번 더 리허설 |

## 🔍 원리 들여다보기 <a id="why"></a>

### 비유 → 정식 용어

| 비유 | 정식 용어 | 이 레슨에서 보는 값 |
|---|---|---|
| 리허설 | 시뮬레이션 `triggerConstantContract` | `result: {"result":true}`, `energy_used: 14,650` |
| 리허설에서 넘어짐 | `REVERT opcode executed` | 노드 원본 `message`, `energy_used: 1,984` |
| 입장권 몇 장 필요한지 세기 | `estimateEnergy` → `energy_required` | 21,975 |
| 입장권 상한 | `feeLimit` (sun) | 2,637,000 sun = 2.637 TRX |
| 무대 오르기 전 손가락 짚기 | 보내기 전 점검표 7항목 | ✅ 7 / ❌ 0 |
| 옆 나라 리허설 | BTTC `estimateGas` | 21,000 gas |

### 실험 1: 출력에서 한 줄 찾기

`npm run l10`을 실행하고 `[3]` 단계에서 다음 두 줄을 찾습니다.

```
  tronweb 예외: REVERT opcode executed
  노드 원본 result: {"result":true,"message":"REVERT opcode executed"}
```

같은 리허설인데 tronweb은 "예외"를 던지고, 노드 원본은 `result: true`라고 말합니다. 노드 입장에서는 "실행은 했다"이고, REVERT였다는 사실은 `message`에만 적혀 있습니다. 노드 응답을 직접 읽는 코드는 `result.result`만 보면 안 되고 `message`가 있는지를 봐야 합니다.

### 실험 2: 환경변수 바꿔 보기

```bash
AMOUNT_USDT=99999999 npm run l10
```

`[2]` 단계의 소액 리허설이 곧바로 `REVERT`로 끝나고, `[4]`의 feeLimit이 계산되지 않으며, `[5]` 점검표의 4번(USDT 잔고 ≥ 금액)과 7번(feeLimit 설정)이 ❌로 바뀝니다. 점검 결과가 `✅ 5 / ❌ 2`가 되면 "보내지 않는다"가 답입니다. `SKIP_BTTC=true`를 붙이면 `[6]`을 건너뜁니다.

### 숫자로 확인하기

- 소액 리허설 `energy_used` 14,650 vs `estimateEnergy` 21,975. 이번 실행에서는 추정이 더 큽니다. feeLimit은 큰 쪽(21,975)으로 잡습니다.
- 소각량 = 21,975 × 100 sun = 2,197,500 sun. 1 TRX = 1,000,000 sun이니 2.1975 TRX. 여기에 1.2를 곱하면 2,637,000 sun = 2.637 TRX.
- 잔고 초과 리허설도 REVERT까지 1,984 에너지를 씁니다. 리허설이라 0원이지만, 실제로 보냈다면 이 에너지만큼 수수료를 냅니다.

### 왜 그렇게 설계했을까?

왜 실패한 트랜잭션에도 수수료를 받을까요? 노드는 결과를 미리 알 수 없어서, 실패를 알기 위해서라도 컨트랙트를 끝까지 실행해야 합니다. 실패가 공짜라면 누구나 실패할 봉투를 무한히 보내 장부지기를 바쁘게 만들 수 있습니다. 대신 노드는 같은 실행을 "장부에 적지 않고" 해 주는 리허설(`triggerConstantContract`)을 공짜로 열어 둡니다. 실패 비용은 보내는 쪽이, 미리 보는 비용은 노드가 지는 구조입니다.

### 비유의 한계 (한 줄)

리허설은 공짜지만 실제 무대(브로드캐스트)는 실패해도 우표를 냅니다. 그리고 리허설은 "지금 이 순간의 장부"로 하는 것이라, 3초 뒤 장부가 바뀌면 리허설 성공이 무대 성공을 보장하지 않습니다.

## 💻 코드로 확인하기 <a id="code"></a>

```bash
npm run l10
# 환경변수: MNEMONIC(없으면 데모), TO(기본 index 1 주소), AMOUNT_USDT(기본 1), SKIP_BTTC=true, LEVEL
```

Nile 읽기 전용입니다. 이 레슨은 `SEND_TX=true`를 붙여도 아무것도 보내지 않습니다. 실행 시간 약 4초. **전체 출력은 [expected-output.txt](./expected-output.txt)를 보세요.** 아래는 핵심 줄만 인용합니다.

### [1/6] 지갑과 리허설 대상 준비

`금액: 1 USDT (= 1,000,000 최소 단위, decimals 6)`. `tronWeb.setAddress(me.address)`로 "누가 묻는지"만 등록하고 개인키는 등록하지 않습니다(리허설에 서명은 필요 없음). 주소를 등록하지 않고 `.call()` 하면 노드가 `owner_address isn't set.` 를 돌려줍니다.

### [2/6] 소액 transfer 리허설 — triggerConstantContract

```
  energy_used: 14,650 (이 호출을 실제로 실행하면 드는 에너지)
  constant_result[0]: 0000000000000000… (32 bytes)
```

`triggerConstantContract(컨트랙트, FUNCTION, {}, params, from)` → `{ result, energy_used, constant_result, transaction, logs }`. `constant_result[0]`이 32바이트 0인 것은 Nile USDT(TetherToken)의 `transfer`가 bool을 안 돌려주기 때문이라, 이 값을 `true/false`로 읽는 코드는 늘 "false"로 오판합니다.

### [3/6] 잔고 초과 transfer 리허설 → REVERT

```
  tronweb 예외: REVERT opcode executed
  노드 원본 result: {"result":true,"message":"REVERT opcode executed"}
```

노드는 `result.result: true` + `message`로 REVERT를 알리고, tronweb은 그 `message`를 보고 예외를 던집니다. 노드 원본은 `POST /wallet/triggerconstantcontract`를 직접 호출해 봅니다(script.js의 `rawSimulate`; 파라미터는 `tronUtils.abi.encodeParams`, 주소는 `41` 없는 20바이트). tronweb 6.5.0에서 실행 확인했고 요청 본문 필드 이름은 노드 HTTP API 규격입니다(확인 필요).

### [4/6] estimateEnergy → feeLimit

```js
const energyFee = Number(params?.find((p) => p.key === 'getEnergyFee')?.value ?? 100); // params = getChainParameters()
const base = Math.max(energyRequired, energyUsed ?? 0);
const burnSun = base * energyFee;
feeLimitSun = Math.ceil(burnSun * FEE_LIMIT_MARGIN); // FEE_LIMIT_MARGIN = 1.2
```

```
  estimateEnergy.energy_required: 21,975
  트랜잭션에 넣는 값: { feeLimit: 2637000 }  // sun 단위
```

`feeLimit`은 sun 단위 정수입니다. TRX 단위 소수(2.637)를 넣으면 tronweb이 빌드 단계에서 예외 `Invalid feeLimit provided`를 던집니다(검수 실행에서 확인, 노드까지 가지 않음). 올바른 값은 `2637000`입니다.

### [5/6] 보내기 전 점검표 7항목

```
  ✅ 5. 대역폭/에너지             에너지 1,323,765 남음 (필요 21,975), 대역폭 11,932 남음 → 스테이킹 에너지로 충분
  점검 결과: ✅ 7 / ❌ 0 / ❓ 0 (7항목)
```

리허설은 "컨트랙트 실행"만 검증합니다. 수신자 활성화·자원·feeLimit·네트워크는 점검표로 따로 확인합니다(`getAccount(to)`가 `{}`면 미활성화 — 처음 받는 주소). 조회 실패 항목은 ❓이고, ❓가 하나라도 있으면 통과가 아닙니다. 남은 에너지는 `(EnergyLimit ?? 0) - (EnergyUsed ?? 0)` — 사용량이 0이면 필드가 생략됩니다.

### [6/6] (선택) BTTC estimateGas 와 비교

같은 열쇠의 0x 주소(`me.evmAddress`)로 BTTC Donau(chainId 1029)에 `estimateGas`를 묻습니다 → `21000 gas × gasPrice 9000000000000000 wei ≈ 189.0 BTT`(테스트넷 값). 레슨 11에서 직접 다룹니다.

### 트론 vs EVM 차이

| 항목 | 트론 | EVM(BTTC 등) |
|---|---|---|
| 결과 미리 보기 | `triggerConstantContract` (서명 없음, from 주소만) | `eth_call` (`provider.call`) |
| 비용 추정 | `estimateEnergy` → `energy_required` | `estimateGas` → gas |
| 비용 단위 | 에너지 × sun (`getEnergyFee` 100 sun/energy) | gas × gasPrice (wei) |
| 상한 | `feeLimit` (sun, 에너지 소각 상한) | `gasLimit` (gas 개수) |
| 실패 표현 | 노드 `result.result: true` + `message: 'REVERT opcode executed'`, tronweb은 예외 | ethers는 revert 시 예외(`CALL_EXCEPTION` 등, 확인 필요) |
| 실패 시 수수료 | 실행에 쓴 에너지·대역폭만큼 (feeLimit 이내) | 쓴 gas만큼 (gasLimit 이내) |

### 함정 1개

`constant_result`를 "반환값"으로 믿고 `transfer`의 bool을 읽으려 하면 Nile USDT에서는 항상 0(false)입니다. 성공 판단은 "예외/REVERT가 없었는가"로 합니다. 노드 원본을 직접 읽을 때는 `result.result`가 `true`여도 `message`가 있으면 실패입니다.

### 도전

- 쉬움: `TO=<자기 주소>`로 실행해 점검표 1번이 ❌로 바뀌는지 확인하세요. 리허설은 성공할까요? 왜 점검표가 따로 필요한지 출력으로 답하세요.
- 어려움: `[3]`을 고쳐 `approve(address,uint256)`을 리허설해 보세요(레슨 9의 허락증). `energy_used`가 `transfer`와 얼마나 다른지, `constant_result`가 0인지 확인하고 이유를 적으세요. (approve 반환값이 bool인지는 확인 필요)

## 🏠 내 생활에서는 <a id="life"></a>

**이 개념이 보이는 자리.** 지갑 앱(TronLink 등)에서 토큰을 보낼 때, 받는 주소와 금액을 넣고 "다음"을 누르면 확인 화면이 나옵니다. 받는 주소와 금액 바로 아래, 보내기 버튼 바로 위에 "예상 수수료"와 "최대 수수료(feeLimit)" 칸이 나란히 있습니다. 토큰(USDT 같은 TRC-20)을 보낼 때는 이 칸에 "에너지" 또는 "리소스"라는 말이 함께 보이기도 합니다.

**그 숫자가 리허설 결과입니다.** 앱은 보내기 전에 노드에게 "이거 되나요, 얼마 드나요?"를 물어보고, 그 답을 이 칸에 적어 줍니다.

안 된다는 답을 받으면 앱은 "이 거래는 실패할 수 있습니다" 같은 빨간 경고를 띄웁니다. 이 경고는 앱이 나를 막는 것이 아니라, 노드가 미리 본 결과를 그대로 옮겨 준 것입니다.

경고가 뜨면 보내지 마세요. 실패한 거래도 수수료는 나갑니다. 반대로 수수료 칸이 아예 보이지 않는 경로라면 무엇을 하는지 알 수 없으니 그때도 멈추세요.

| 이런 요청이 오면 | 사기인가? | 이유 |
|---|---|---|
| 앱이 "이 거래는 실패할 수 있습니다"라고 경고하는데, 상대가 "괜찮으니 그냥 보내세요"라고 재촉한다 | 예 | 리허설이 넘어졌다고 알려 준 것입니다. 실패해도 수수료는 나가고, 재촉하는 쪽이 이득을 봅니다 |
| 앱이 "예상 수수료 약 2 TRX"를 보여 주고, 내 TRX 잔고가 그보다 많다 | 아니오(보내도 됨) | 리허설이 통과했고 연료도 충분합니다. 다만 받는 주소와 나라는 내가 확인해야 합니다 |
| "수수료 없이 보내 주는 사이트"라며 보내기 대신 서명만 하라고 한다 | 예 | 리허설·수수료 표시가 없는 경로는 무엇을 하는지 알 수 없습니다. 레슨 8·9의 허락증일 수 있습니다 |

**사기 유형 1개: "실패 수수료 낚시".** 일부러 실패할 봉투(잔고보다 큰 금액, 잘못된 컨트랙트)를 여러 번 보내게 만들어 그때마다 수수료를 태우게 하거나, "실패했으니 내가 고쳐 줄게, 열쇠 줘"로 이어집니다. 앱의 실패 경고는 사기가 아니라 방패입니다. 경고를 무시하라는 사람이 여우 씨입니다.

**오늘 실천 습관 1개:** 토큰을 보내기 전에 "예상 수수료" 숫자를 소리 내어 읽고, 내 TRX 잔고가 그보다 많은지 확인하세요. 빨간 경고가 보이면 화면을 캡처하고 보내지 마세요. 처음 보내는 주소라면 아주 조금만 먼저 보내 받는 쪽 우편함이 열려 있는지 확인하는 것도 같은 습관입니다(규칙 6).

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 10. 앱이 "실패할 것 같다"고 하면 보내지 않는다.**

**해야 할 것**
- ✅ 보내기 전에 예상 수수료와 실패 경고를 읽는다. (리허설 결과)
- ✅ 점검표 7칸(주소, 수신자, TRX, 토큰 잔고, 연료, 나라, feeLimit)을 짚는다.
- ✅ feeLimit은 예상보다 조금 넉넉하게, 그러나 필요 이상으로 크지 않게.

**절대 하지 말 것**
- ❌ 실패 경고를 보고도 "한 번만 더" 보내지 않는다. 실패도 수수료가 나간다.
- ❌ 리허설 성공만 믿고 나라·받는 주소 확인을 건너뛰지 않는다.
- ❌ "실패했으니 고쳐 줄게, 열쇠 줘"라는 말에 응하지 않는다.
