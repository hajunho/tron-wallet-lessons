## 🧒 이야기로 시작 <a id="story"></a>

달력에 동그라미가 있어요.

"이번 달 점검 같이 할까?"

엄마와 토리가 장부 앞에 서요.

사탕 수, 허락증, 최근 편지를 봐요.

마지막은 열쇠 구멍 주인(계정 권한)이에요.

모두 토리 것이에요.

"레슨 3의 그 상자 기억나니?"

"주문이 새면 구멍 주인이 바뀐단다."

**핵심 한 문장:** 한 달에 한 번 점검, 사고가 나면 순서대로, 혼자 끙끙대지 않기.

**엄마 아빠에게 물어보기:** "우리 집은 한 달에 한 번 무엇을 점검하나요?"

**진행 (30분) — 교사 발화까지**

1. **점검표 채우기 (7분).** 칠판에 "토리의 상자"를 그리고 네 칸(사탕 수 / 허락증 / 최근 편지 / 열쇠 구멍 주인)에 카드 A의 값을 적는다. 학생은 워크시트 1번 표에 값을 옮겨 적고 ✅ 칸을 초록으로 칠한다.
   - 교사: "네 칸이 다 초록이면 이번 달 점검 끝!"
2. **몰래 바꾼 칸 찾기 (8분).** 학생이 눈을 감은 사이 카드 B·C·D 중 하나로 칸 하나를 바꾼다. 학생은 ⚠️ 칸을 주황으로 칠하고 워크시트 2번에 규칙 번호를 적는다(B → 규칙 1·13, C → 규칙 9, D → 규칙 7·13). 세 번 반복한다.
   - 교사: "어느 칸이 바뀌었을까? 그건 몇 번 규칙이야?"
3. **사고 대응 줄 세우기 (7분).** 다섯 명이 사고 대응 카드를 한 장씩 들고 앞에 나와 순서대로 선다. 순서가 틀리면 처음부터 다시.
   - 교사: "여우 씨가 '내가 고쳐 줄게, 열쇠 줘'라고 하면?" → 학생: "1번 멈추기! 여우 씨 말 안 들어요!"
4. **13규칙 뽑기 (6분).** 번호가 보이게 펼친 카드를 한 장 뽑아 규칙 문장을 끝까지 말한다. 막히면 뒷면을 보고 따라 읽은 뒤 다시 뒤집는다. 반 전체가 13장을 한 번씩 말하면 통과.
   - 교사: "13번은? 그래, 한 달에 한 번 점검!"
5. **졸업장과 다음 점검일 (2분).** 졸업장에 이름을 쓰고, 워크시트 4번에 한 달 뒤 날짜와 "함께 점검할 사람"을 적는다.
   - 교사: "혼자 끙끙대지 않기. 그 칸에 적은 사람이 같이 볼 사람이야."

### 비유는 어디까지 맞을까요?

| 비유 | 정식 용어 | 스크립트에서 보이는 자리 |
|---|---|---|
| 보물상자 점검 | 지갑 감사(audit) — 읽기 전용 조회 모음 | 전체 `[1]`~`[6]` |
| 열쇠 구멍 주인 | 계정 권한(owner/active permission, threshold, weight) | `[2]` owner 키 #1 / active #1 키 #1 |
| 허락증 | approve / allowance | `[4]` allowance |
| 최근 편지 | 최근 트랜잭션(TronGrid REST) | `[5]` 시각 / 종류 / 결과 / 상대 / 금액 / 수수료 |
| 입장권과 맡긴 사탕상자 | 대역폭·에너지 / 스테이킹(frozenV2) | `[3]` |
| 점검 네 칸: 사탕 수 / 허락증 / 최근 편지 / 열쇠 구멍 주인 | 잔고 / 허락(allowance) / 최근 거래 / 권한(permission) | `[1]` / `[4]` / `[5]` / `[2]` |
| ✅ / ⚠️ / ❓ 개수 | 통과 / 경고 / 직접 확인·조회 실패 | `[6]` 점검 항목: 9개 |

### 실험 1: 출력에서 한 줄 찾기 — 열쇠 구멍 주인은 누구인가요?

스크립트를 실행하고 `[2]`에서 두 줄을 찾습니다.

```
  owner 키 #1: 41156f4463ce90ac11e1855ff99e4273806ad847cf (weight 1)
  내 hex 주소: 41c8599111f29c1e1e061265b4af93ea1f274ad78a
```

앞 6글자만 비교해 보세요. `41156f`와 `41c859`. 다릅니다. 정상 계정이라면 owner 키가 딱 하나이고 그 값이 내 hex 주소와 같아야 합니다. 데모 주소는 니모닉이 전 세계에 공개되어 있어서, 누군가 먼저 권한 키를 자기 것으로 바꿔 두었습니다. 그래서 `[6]`의 점검 항목 9개 중 ⚠️가 2개(owner, active)입니다. 나머지 7개는 ✅인데도 이 지갑은 "내 것"이 아닙니다. 점검은 개수가 아니라 **어느 항목**이 ⚠️인지가 중요합니다.

### 실험 2: 환경변수 바꿔보기 — 다른 상자, 다른 상대

```bash
npm run l13 -- TSeJkUh4Qv67VNFwY8LaAxERygNdy6NQZK         # 1) 같은 니모닉의 두 번째 주소
SPENDERS=TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf npm run l13  # 2) 허락증 확인 상대 바꾸기
ADDRESS=<npm run new-wallet 로 만든 주소> npm run l13      # 3) TRX 를 받은 적 없는 새 주소
```

1)에서는 `[2]`의 owner 키가 데모 주소와 **같은** `41156f…47cf`로 나옵니다. 같은 사람이 두 주소의 권한을 모두 가져갔다는 뜻입니다. 주소를 인자로 주면 니모닉이 없어 허락증 점검이 빠지고 항목이 9개→8개(✅ 6 / ⚠️ 2)가 됩니다. allowance 도 보려면 `SPENDERS=` 를 함께 주세요. 2)에서는 `[4]`에 그 상대에 대한 allowance 한 줄이 나옵니다(0이면 ✅). 3)에서는 `[1]`에 `getAccount 결과가 빈 객체 {}` ⚠️가 나오고, `[2]`는 권한 정보가 없다는 안내로 건너뛰고, `[3]`은 ❓(활성화 전에는 대역폭을 점검할 수 없음)가 되어 항목이 6개(✅ 3 / ⚠️ 2 / ❓ 1)로 줄어듭니다. `LEVEL=teen npm run l13`으로 실행하면 💬 해설이 중고등용으로 바뀝니다.

### 왜 그렇게 설계했을까요?

왜 트론은 계정 권한을 바꿀 수 있게 만들었을까요? 회사 지갑처럼 "세 명 중 두 명이 도장을 찍어야 보내진다"(threshold 2, 키 3개)를 체인이 직접 지원하기 위해서입니다(threshold·weight 필드는 확인됨, 실제 다중서명 전송은 확인 필요). 편리한 기능이지만, 같은 기능을 공격자가 쓰면 "원래 열쇠를 무력화"하는 도구가 됩니다. 그러면 질문. 권한이 바뀐 것을 앱 화면만 보고 알 수 있을까요? 잔고는 그대로 보이는데요. 그래서 한 달에 한 번 장부에서 권한을 직접 읽는 점검이 필요합니다. 진짜 열쇠는 복사해도 둘 다 진짜지만 니모닉은 복사된 순간 남의 것이기도 하니, "잃어버리지 않기"만으로는 부족하고 "새지 않았는지 확인하기"가 점검 항목에 들어갑니다.

### 비유의 한계

열쇠 구멍은 못 바꾸지만 계정 권한은 바꿀 수 있습니다.

### 점검 결과를 모으는 구조 — ✅ / ⚠️ / ❓ 세 갈래

```js
const checks = []; // { label, state } — 'ok' ✅ / 'warn' ⚠️ / 'todo' ❓(조회 실패·사람이 직접 확인)
const pass = (label, msg) => { checks.push({ label, state: 'ok' }); print.ok(msg ?? label); };
const flag = (label, msg) => { checks.push({ label, state: 'warn' }); print.warn(msg ?? label); };
const todo = (label, msg) => { checks.push({ label, state: 'todo' }); console.log('  ❓', msg ?? label); };
```

각 단계는 예외로 멈추지 않고 결과만 쌓습니다. 네트워크 호출은 `tryCall`로 감싸 실패하면 `null`을 돌려주고(429는 "잠시 후 다시" 안내), 그 항목은 ✅가 아니라 **❓(점검 미완료)** 로 들어갑니다. 조회가 실패했는데 "통과"로 보이는 것이 점검 스크립트에서 가장 위험하기 때문입니다. 같은 이유로 성공·경고 분기가 같은 `label`을 쓰도록 맞췄습니다(달마다 JSON으로 비교할 때 항목이 '삭제+추가'로 보이지 않게).

### [1/6]·[2/6] 기본 정보와 계정 권한 — 이 레슨의 핵심

```
  ⚠️  다른 키가 권한을 가짐! owner 키 1개 중 내 주소가 없습니다.
  ⚠️  active 권한에 다른 키가 있습니다. 권한 키가 내 것이 아니므로 원래 열쇠로는 전송이 거부될 것입니다(실제 브로드캐스트는 확인하지 않았습니다).
```

```js
const ownerIsMe = ownerKeys.length === 1 && ownerKeys[0].address.toLowerCase() === hexAddress.toLowerCase();
// active_permission 은 배열이라 모든 항목이 "키 1개 = 내 주소" 여야 정상으로 본다(activeIsMe).
```

`getAccount`의 `owner_permission`은 `{ permission_name, threshold, keys: [{ address, weight }] }`, `active_permission`은 같은 모양의 배열입니다(항목마다 `operations` 비트마스크가 있음). 정상 계정은 두 곳 모두 키가 하나이고 그 값이 내 hex 주소입니다. 데모 주소는 두 곳 모두 `41156f…47cf`라 ⚠️ 2개가 실제로 나옵니다. 이것이 Lesson 03에서 "왜인지는 나중에"라고 미뤄 둔 답입니다. `getAccount`가 `{}`(미활성화)인 것과 호출이 실패한 것(`null`)은 구분합니다. 후자는 ❓ `계정 권한 조회`로 올라가 "점검 미완료"가 됩니다.

### [3/6]·[4/6] 자원·스테이킹과 허락증

```
  맡긴 TRX (frozenV2): type 없음(대역폭 추정)=17949 TRX, ENERGY=17950 TRX
  참고: type 이 없는 항목을 대역폭으로 보는 것은 관례입니다(확인 필요).
  ✅ TSeJkUh4Qv67VNFwY8LaAxERygNdy6NQZK 에게 남은 허락 0. 깨끗합니다.
```

`getAccountResources`는 사용량이 0이면 `freeNetUsed`/`NetUsed`/`EnergyUsed` 필드를 생략하므로 `?? 0`이 필수입니다. `frozenV2`는 Stake 2.0 스테이킹이고, `type` 없는 항목을 대역폭으로 보는 것은 관례입니다(확인 필요). `amount`가 없는 항목(예: `{"type":"TRON_POWER"}`)은 "0 TRX 를 맡겼다"가 아니라 맡긴 금액이 없는 항목이라 걸러냅니다. 미활성 계정은 한도 필드 자체가 없어 이 단계를 ❓로 두고, 그 상태의 전송은 대역폭과 무관하게 `account does not exist`로 거부됩니다(Lesson 12). 허락증은 `allowance(owner, spender)`가 상대별 값이라 "내가 허락한 전체 목록"을 주는 함수가 없어, `SPENDERS`에 의심되는 컨트랙트 주소를 직접 넣습니다(무제한 판정 기준 `UNLIMITED / 2n`은 `lib/guard.js`와 같은 값). `SPENDERS` 형식 검증은 `main()` 맨 앞에서 끝냅니다. `[4]` 중간에서 예외를 던지면 오타 하나에 요약·사고 대응 순서·졸업 체크리스트가 통째로 사라지므로, 잘못 적은 항목만 경고하고 건너뜁니다.

### [5/6]·[6/6] 최근 거래 — 방향(→ / ←)을 먼저 센다, 그리고 요약

```
  2026. 9. 12. 오후 6:22:09 | TransferContract | SUCCESS | ← TBdYXt…anu1 | 0.0001 TRX | 0.265 TRX
  방향별: 내가 보낸 것(→) 0건 / 남이 나에게 한 것(←) 5건
  ✅ 최근 목록에 내가 보낸(→) 거래가 없습니다. 직접 확인할 것이 없습니다.
```

`GET /v1/accounts/{T주소}/transactions?limit=5&only_confirmed=true`는 `{ data: [{ txID, ret: [{ contractRet, fee }], net_fee, energy_fee, raw_data: { contract: [{ type, parameter: { value } }] }, block_timestamp }] }`를 돌려줍니다. 수수료는 두 자리에서 볼 수 있습니다. 응답 최상위의 `net_fee`·`energy_fee`, 그리고 `ret[0].fee` 입니다. Nile 응답으로 직접 확인한 결과 `ret[0].fee` 는 두 값의 합과 같았습니다(`net_fee 265000` + `energy_fee 0` = `ret[0].fee 265000`). 어느 쪽을 읽어도 되지만, 항목별로 나눠 보려면 최상위 두 값을 쓰세요. 종류별로 `value`의 필드가 달라서(`to_address` / `receiver_address` / `contract_address`) `summarizeTx`가 상대와 금액을 골라 뽑고, `owner_address === 내 hex`로 방향을 가릅니다. **`←`는 남이 나에게 한 거래이므로 유출 신호가 아닙니다.** 데모 주소의 5건은 전부 `←`(남이 보낸 전송, 남이 걸어 준 Delegate/UnDelegate)라 "내가 보낸 거래 확인"이 ✅입니다. 보낸 것이 1건이라도 있으면 "기억에 있나"는 코드가 판정할 수 없으니 ❓로 올려 사람이 txID로 확인하게 합니다. 두 번째 표는 `/transactions/trc20`이고, `token_info.address`가 Nile USDT가 아니면 같은 `토큰 컨트랙트` 항목에 ⚠️를 냅니다. 이 표는 시간이 지나면 값이 바뀝니다.

`[6]`은 이 결과를 세어 `점검 항목: 9개 — ✅ 7개 / ⚠️ 2개 / ❓ 0개`로 요약하고(⚠️는 owner 권한·active 권한), 그 아래에 사고 대응 5순서와 13규칙 체크리스트를 그대로 인쇄합니다. 마지막 줄은 `🎓 졸업을 축하합니다. ➡️ 다음: 한 달 뒤 npm run audit 으로 다시 점검`입니다.

### 트론 vs EVM 차이

| | 트론(Nile) | EVM(BTTC Donau 등) |
|---|---|---|
| 계정 권한 | owner/active permission, threshold, weight를 체인이 지원. **바꿀 수 있음** | 이 레슨에서 확인하지 않았다(BTTC Donau 에서 확인한 범위는 잔고·gasPrice·estimateGas) |
| 허락증 확인 | `allowance(owner, spender)` (TRC-20) | `allowance(owner, spender)` (ERC-20과 같은 ABI) |
| 최근 거래 조회 | TronGrid REST `/v1/accounts/{addr}/transactions` | 노드 RPC에는 없음. 탐색기 API 사용(확인 필요) |
| 자원 상태 | 대역폭·에너지·스테이킹(`getAccountResources`) | 가스비를 낼 잔고를 `getBalance`·`getFeeData().gasPrice`로 확인 |

### 함정 1개: `getAccountResources`의 "사용량 0"은 필드 생략이다

`freeNetUsed`, `NetUsed`, `EnergyUsed`는 값이 0이면 응답에 아예 없습니다. `res.freeNetLimit - res.freeNetUsed`를 그대로 쓰면 `600 - undefined = NaN`이 되어 "남은 대역폭 NaN"이 출력되고, `NaN > 0`은 false라 멀쩡한 계정에 ⚠️가 붙습니다. 스크립트는 모든 사용량에 `?? 0`을 붙입니다. 같은 이유로 `account.frozenV2`, `account.unfrozenV2`, `p.keys`도 `?? []`로 받습니다.

### 도전 2개

- **쉬움:** `[4]`의 `SPENDERS`에 Lesson 09에서 approve했던 상대를 넣고, allowance가 0이 아니면 ⚠️ 문구에 "approve(0)을 보내려면 `npm run l09`"를 덧붙여 보세요. 그다음 여러 상대를 쉼표로 넣어 표로 출력하도록 바꿔 보세요.
- **어려움:** `checks` 배열을 JSON 파일(`out/13-audit-YYYY-MM-DD.json`)로 저장하고, 다음 달 실행 때 지난 파일과 비교해 "지난달 ✅였는데 이번 달 ⚠️(또는 ❓)로 바뀐 항목"만 따로 출력하세요. `label`이 분기마다 같아야 비교가 된다는 것을 직접 확인하게 됩니다. 권한 키가 바뀐 경우를 가장 크게 표시해야 합니다.

## 🏠 내 생활에서는 <a id="life"></a>

지갑 앱(TronLink 등)의 첫 화면은 잔고만 보여 줍니다. 권한이 바뀌었는지, 남은 허락(approve)이 있는지는 첫 화면에 없습니다. 그래서 한 달에 한 번, 탐색기에서 내 주소를 검색해 네 가지를 보세요. 잔고, 권한(Permission), 허락(approve), 최근 거래.

- **잔고:** 앱 숫자와 탐색기 숫자가 같은지 대조하세요(규칙 3).
- **권한:** 탐색기 주소 페이지의 권한 항목에 내 주소가 아닌 키가 있으면, 그 지갑은 이미 내 것이 아닙니다. 바로 아래 "사고 대응 순서"로 가세요.
- **허락(approve):** DEX·브릿지에서 "승인"을 누른 적이 있다면 남은 허락을 확인하고, 다 썼으면 0으로 돌려놓으세요(규칙 9). 탐색기의 승인 관리 메뉴 위치는 확인 필요.
- **최근 거래:** 내가 **보낸**(→, 보낸 사람이 내 주소인) 거래 중 기억이 없는 것이 하나라도 있으면 열쇠가 샌 것입니다. 받은 거래(←)나 남이 걸어 준 위임, 모르는 곳에서 들어온 먼지 같은 입금은 유출 신호가 아닙니다(다만 그 토큰은 만지지 마세요).

점검은 남의 도움 없이 혼자 할 수 있는 일입니다. 주소만 있으면 누구나, 열쇠 없이, 탐색기에서 이 네 가지를 볼 수 있습니다. 그래서 "점검해 드릴게요"라며 복구 구문을 묻는 사람은 처음부터 점검이 목적이 아닙니다.

**사고 대응 순서(스크립트 `[6]`과 같음):** ① 멈추기(더 이상 서명하지 않기, "고쳐 준다"는 사람 말 듣지 않기) → ② 새 지갑 만들기(새 12단어를 종이에) → ③ 자산 옮기기(TRX를 먼저 조금 보내 새 주소를 활성화하고, 나머지는 소액 먼저) → ④ 허락 취소(approve 0, 권한이 이미 바뀌었다면 옛 지갑은 버리기) → ⑤ 알리기·신고(가족·동료, 거래소·서비스, 수사기관. 신고처는 나라마다 다름, 확인 필요).

**이런 요청이 오면 사기인가?**

| 상황 | 사기? | 이유 |
|---|---|---|
| "정기 보안 점검입니다. 복구 구문을 입력하면 지갑 상태를 진단해 드립니다." | 예 | 점검은 주소만으로 누구나 할 수 있습니다. 복구 구문을 묻는 점검은 없습니다(규칙 1). |
| "권한이 바뀐 것 같네요. 제가 원래대로 고쳐 드릴게요. 개인키만 보내 주세요." | 예 | 권한이 바뀐 지갑은 고치는 것이 아니라 버리고 새로 만드는 것입니다. "고쳐 준다"는 사람은 사기입니다(규칙 12). |
| 내가 직접 탐색기에서 내 주소를 검색해 잔고·권한·최근 거래를 봤습니다. | 아니오 | 이것이 한 달 점검입니다. 아무에게도 아무것도 보내지 않았습니다. |

**사기 유형 1개 — "고쳐 드립니다" 복구 대행:** 사고를 당한 사람이 가장 급할 때 나타납니다. "권한 복구", "자산 회수", "해킹 추적" 같은 말로 개인키·복구 구문·선금을 요구합니다. 권한이 바뀐 지갑은 원래 열쇠로는 아무것도 못 보내므로, 그 사람이 할 수 있는 일도 없습니다. 있다면 그 사람이 바로 권한을 가져간 사람입니다.

**오늘 실천 습관 1개:** 달력에 한 달 뒤 날짜를 정해 "지갑 점검"이라고 적으세요. 그날 탐색기에서 잔고·권한·허락·최근 거래 네 가지를 보고, 이상하면 혼자 끙끙대지 말고 바로 가족이나 동료에게 말하세요.

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 13. 한 달에 한 번 점검, 사고가 나면 순서대로, 혼자 끙끙대지 않기.**

**해야 할 것**
- ✅ 한 달에 한 번, 탐색기에서 잔고·권한·허락·최근 거래 네 가지를 본다.
- ✅ 권한 키가 내 주소가 아니면 그 지갑은 버리고 새 지갑으로 옮긴다(TRX 먼저, 소액 먼저).
- ✅ 사고가 나면 순서대로: 멈추기 → 새 지갑 → 자산 옮기기 → 허락 취소 → 알리기·신고.

**절대 하지 말 것**
- ❌ "점검해 드린다"며 복구 구문·개인키를 묻는 사람에게 답하지 않는다.
- ❌ "고쳐 준다"는 사람에게 선금이나 열쇠를 주지 않는다.
- ❌ 이상한 것을 보고도 혼자 끙끙대며 숨기지 않는다.
