## 🧒 이야기로 시작 <a id="story"></a>

"열쇠를 넣으면 우편함 번호(주소)가 나와."

**무장비 5분 버전**

칠판만 있으면 됩니다. 교사가 규칙을 말합니다. "이름의 첫 자음이 ㄱ이면 1, ㄴ이면 2 … ㅎ이면 14. 글자마다 그 숫자를 더하고, 마지막에 10으로 나눈 나머지만 말하세요." 학생이 차례로 "7!" "3!" "7!" 하고 말합니다. 교사가 "숫자가 7인 사람, 손!" 하면 여러 명이 손을 듭니다. 숫자(주소)만 듣고는 이름(열쇠)을 알 수 없다는 것을 확인합니다. 이어서 이름 한 글자만 바꿔 숫자가 바뀌는지 해 보고, "숫자는 말해도 되고 이름은 안 된다"로 마무리합니다. 이 놀이의 숫자는 0~9 열 가지뿐이라 겹치는 사람이 많지만, 진짜 주소는 20바이트라 겹칠 걱정이 없습니다.

**발문 3개**

1. 같은 이름을 넣었는데 다른 띠가 나올 수 있을까요? 왜 그럴까요?
2. 띠를 보고 이름을 맞히려면 어떻게 해야 할까요? 이름이 1만 개라면 몇 번을 칠해 봐야 할까요?
3. 우편함 번호는 친구에게 알려 줘도 되는데, 열쇠는 왜 안 될까요?

**놀이터 링크:** [우편함 번호 엑스레이 (T ↔ 41 ↔ 0x)](../../playground/address-xray.html) — 오타 주소·닮은 주소를 화면에서 바로 비교합니다. [주사위 → 12단어 주문](../../playground/dice-to-words.html)의 마지막 단계도 이 레슨의 "열쇠 → 주소"입니다. 두 놀이터는 ethers 를 CDN 에서 받으므로 **인터넷이 필요**합니다.

"네트워크가 필요 없다"는 것은 `npm run l02` 스크립트 쪽 이야기입니다. 아래 `npm run l02` 한 번이면 끝납니다.

**손으로 한 걸음 더 (중고등).** 워크시트 C 를 채우기 전에 종이에 이렇게 적어 보세요. ① 내 주소 34글자를 네 글자씩 끊어 아홉 칸으로 나눈다. ② 첫 글자 `T` 와 두 번째 글자에 동그라미를 친다. ③ 두 번째 글자가 될 수 있는 글자는 58종이 아니라 25종(9, A~Z 에서 I·O 제외)뿐입니다. 페이로드 첫 바이트가 `0x41` 로 고정이라 base58 첫 자리가 제한되기 때문입니다. ④ 그래서 "앞 세 글자를 맞추는 데 58² ≈ 3364번"이 아니라 약 25 × 58 ≈ 1450번입니다(무작위 키 2만 개로 확인).

**왜 주소를 한 글자씩 대조해야 하나요.** 앞 4글자와 뒤 4글자만 같은 주소는 만들기가 생각보다 쉽습니다. 가운데를 비교하지 않으면 "닮은 주소"에 그대로 보냅니다. 놀이터의 "닮은 주소 찾기"가 이 장면을 보여 줍니다.

## 🔍 원리 들여다보기 <a id="why"></a>

### 비유 → 정식 용어

| 비유 | 정식 용어 | 이 레슨에서 확인하는 값 |
|---|---|---|
| 열쇠 | 개인키 (32바이트) | `b5a4…9a28` (마스킹, `SHOW_SECRETS=true`로 전체) |
| 열쇠의 공개해도 되는 반쪽 | 공개키 (secp256k1, 비압축 65바이트) | `0x04ff21…dc83` |
| 특별한 기계 | 해시 (keccak256) | 결과 32바이트 중 뒤 20바이트만 사용 |
| 우편함 번호 | 주소 (T로 시작, 34글자, base58check) | `TUEZSdKsoDHQMeZwihtdoBiN46zxhGWYdH` |
| 숨어 있는 옆 나라 번호 | EVM 주소 (0x + 40hex) | `0xC8599111F29c1e1E061265b4AF93eA1F274aD78A` |

### 왜 한 방향일까?

개인키에서 공개키로 가는 계산은 "큰 수 곱하기"입니다. 반대로 공개키에서 개인키를 찾는 계산은 사실상 방법이 없습니다. 그다음 keccak256 해시는 공개키 64바이트(x, y)를 32바이트로 뒤섞는데, 출력에서 입력을 찾는 방법이 없고 입력 1비트만 달라도 출력이 전부 달라집니다. 스크립트 [2]단계에서 개인키 마지막 한 글자만 바꾼 "이웃 열쇠"의 주소가 `TCXechLiHQuF4J8DroYoc1KhSVutYVWxic`로 완전히 달라지는 것을 볼 수 있습니다.

주소는 20바이트 = 160비트라 가짓수가 2^160 ≈ 1.46×10^48입니다. 세상 모든 사람이 평생 주소를 만들어도 겹칠 걱정은 하지 않아도 되는 크기입니다.

### 실험 1: 출력에서 한 줄 찾기

`npm run l02`를 실행하고 [2]단계에서 `✅ 손으로 만든 주소 == TronWeb 주소 (34글자, T로 시작)` 줄을 찾으세요. 이 줄 위 7줄 중 앞 6줄이 "손으로 만든" 과정이고, 7번째 줄(`TronWeb.address.fromPrivateKey`)이 라이브러리 결과입니다. keccak256 결과 `0x16030ddb…274ad78a`의 뒤 40글자(20바이트)가 `c8599111…274ad78a`이고, 앞에 `41`을 붙인 21바이트를 두 번 sha256 해서 앞 4바이트 `1912f84c`를 체크섬으로 붙인 뒤 base58로 바꾸면 `TUEZ…YdH`가 됩니다. 라이브러리 없이 계산해도 같은 주소가 나옵니다.

### 실험 2: 환경변수 바꿔 보기

```bash
# 1) 열쇠를 가리지 않고 전부 보기
SHOW_SECRETS=true npm run l02

# 2) 해설을 중고등용으로
LEVEL=teen npm run l02

# 3) 내 연습용 니모닉으로 (npm run new-wallet 로 만든 것)
MNEMONIC="여기에 12단어" npm run l02
```

1)번은 데모 니모닉일 때만 마음 편히 쓰세요. `lib/wallet`이 `.env`를 읽으므로 **`.env`에 내 니모닉이 들어 있으면 내 12단어와 개인키가 그대로 화면에 찍힙니다.** 화면 공유·녹화·수업 시연 중에는 쓰지 않습니다. 3)번을 하면 [4]단계의 주소 5개와 [6]단계의 "앞 3글자가 같은 주소"가 전부 달라지고, [5]단계의 "이더 경로" 주소도 달라지지만 두 경로가 다르다는 결론은 그대로입니다. 몇 번 시도 만에 닮은 주소가 나오는지도 비교해 보세요(평균 약 1,450번).

### 왜 그렇게 설계했을까?

공개키 65바이트를 그대로 주소로 쓰면 안 될까요? 트론(그리고 이더리움)은 해시의 뒤 20바이트만 씁니다. 짧아서 적기 쉽고, 앞에 붙는 `41`과 뒤에 붙는 체크섬 4바이트 덕분에 "트론 주소인지"와 "오타가 있는지"를 라이브러리가 바로 알 수 있습니다. 반대로 20바이트로 줄였기 때문에 주소만 보고는 공개키조차 알 수 없습니다. 이 설계의 대가는 무엇일까요? (힌트: [6]단계의 "앞 3글자가 같은 주소"가 631번 만에 나옵니다.)

**비유의 한계 한 줄**: 우편함은 열쇠 하나에 하나지만, 주소는 같은 12단어에서 경로 인덱스만 바꿔 얼마든지 여러 개 만들 수 있습니다([4]단계).

### [1/6]·[2/6] 경로 → 키 → 손으로 만든 T주소

```
  ✅ TronWeb.fromMnemonic 의 개인키·비압축 공개키와 정확히 일치
  keccak256 결과(32바이트): 0x16030ddba3ad8871035229b3c8599111f29c1e1e061265b4af93ea1f274ad78a
  체크섬 = sha256(sha256(21바이트)) 앞 4바이트: 1912f84c
  ✅ 손으로 만든 주소 == TronWeb 주소 (34글자, T로 시작)
  개인키 마지막 한 글자만 바꾼 "이웃 열쇠"의 주소: TCXechLiHQuF4J8DroYoc1KhSVutYVWxic
```

`walletFromMnemonic(mnemonic, 0)` = ethers `HDNodeWallet.fromPhrase`로 `m/44'/195'/0'/0/0`(195 = TRON coin_type). 압축 공개키는 x + y의 홀짝(33B), 비압축은 x, y 모두(65B) — `TronWeb.fromMnemonic`도 같은 경로가 기본값이라 값이 일치한다. 주소는 tronweb 없이 `ethers.keccak256` + sha256 + `ethers.encodeBase58` 만으로 만들 수 있다.

```js
const payload = '41' + ethers.keccak256(xy).slice(-40); // xy = 비압축 공개키에서 04 를 뗀 64바이트
return base58check(payload);                            // payload + sha256d 앞 4바이트 → base58
```

### [3/6] T ↔ 41hex ↔ 0x

```
  TronWeb.address.toHex: 41c8599111f29c1e1e061265b4af93ea1f274ad78a
  '41' 을 떼고 '0x' 를 붙이면: 0xC8599111F29c1e1E061265b4AF93eA1F274aD78A
  ✅ T주소의 20바이트 == 같은 열쇠의 EVM(0x) 주소. 트론 주소는 "0x주소 + 프리픽스 41 + 체크섬" 이다
```

`toHex(T)` = `'41' + 40hex`, `fromHex`는 그 반대. `41`을 떼고 `ethers.getAddress('0x' + hex40)`을 거치면 ethers가 만드는 대소문자 섞인 체크섬 표기(EIP-55, 확인 필요)가 되고, `lib/wallet.js`의 `evmAddress`와 같다. 레슨 11에서 이 0x주소로 BTTC 잔고를 조회한다.

### [4/6]·[5/6] 인덱스 0~4, 그리고 다른 경로

```
  1     | m/44'/195'/0'/0/1        | TSeJkUh4Qv67VNFwY8LaAxERygNdy6NQZK | 0xb6E708a39781c96Bd399C7657780Ff9Fe9F052A8
  ✅ 주소 5개가 모두 다르다. 열쇠도 각각 다르지만 12단어 하나로 전부 다시 만들 수 있다
  이더 경로 m/44'/60'/0'/0/0: TPrkFhZ8LH8Mruco8vXyA496TaeFBrbmeU  (0x 표기: 0x9858EfFD232B4033E47d90003D41EC34EcaEda94)
```

`walletFromMnemonic(mnemonic, i)`의 `i`가 경로 마지막 칸(BIP-44)이고, 앱의 "계정 추가"가 이것이다. index 1 `TSeJ…NQZK`는 레슨 5~6의 기본 수신자다(트론은 자기 자신에게 못 보낸다). 경로를 `60'`으로 바꾸면 트론 형식 주소는 나오지만 전혀 다른 주소 — "복구했더니 잔고 0"의 흔한 원인.

### [6/6] 오타 감지와 닮은 주소

```
  TronWeb.isAddress(오타): false
  앞 3글자가 같은 유효한 주소: TUEBjFNjV3NuZnnZmPgtUxGBBQbMxSPAWb  (631번 시도)
  TronWeb.isAddress(닮은 주소): true
```

닮은 주소는 `sha256('lookalike:' + i)`를 개인키로 삼아 `tiny-secp256k1`로 앞 3글자를 맞춘 것이다(결정적이라 매번 631번). base58은 58종이지만 페이로드 첫 바이트가 `0x41`로 고정이라 **T 다음 글자는 25종(9, A~Z 중 I·O 제외)만** 나온다 → 앞 3글자 평균 약 25×58 ≈ 1,450번, 앞 4·뒤 4(T 제외 7글자) 약 25×58^6 ≈ 9.5×10^11번. 체크섬은 "실수"만 잡고 "고의"는 못 잡는다.

### 트론 vs EVM 차이

| | 트론 | EVM(이더리움·BTTC) |
|---|---|---|
| 키·곡선 | secp256k1, 같은 개인키 | 같음 |
| 해시 | keccak256(공개키 64바이트) 뒤 20바이트 | 같음 |
| 표기 | `41` + 20바이트 + sha256d 체크섬 4바이트 → base58 (T로 시작, 34글자) | `0x` + 20바이트 hex (42글자), 대소문자 섞인 체크섬 표기 |
| 오타 검출 | base58check 실패 → `isAddress` false | 대소문자 체크섬(EIP-55). 소문자만 쓰면 검출 안 됨 (확인 필요) |
| 기본 경로 | `m/44'/195'/0'/0/0` | `m/44'/60'/0'/0/0` |

### 함정 1개

`toHex`는 소문자 hex(`41c8599111…`), `evmAddress`는 대소문자 섞인 체크섬 표기(`0xC8599111F29c1e…`). `'0x' + hex41.slice(2) === me.evmAddress`는 같은 주소인데도 **false**다. 그래서 스크립트는 `toLowerCase()` 또는 `ethers.getAddress()`로 맞춘 뒤 비교한다. 주소 문자열 비교에서 가장 자주 나는 오류.

### 도전

- **쉬움**: [4]단계 표를 index 0~9로 늘리고, `TronWeb.address.toHex` 결과의 앞 두 글자가 모두 `41`인지 확인하는 줄을 추가하세요.
- **어려움**: `ethers.decodeBase58`로 T주소를 25바이트로 되돌려 앞 21바이트의 sha256(sha256()) 앞 4바이트가 뒤 4바이트와 같은지 보는 `myIsAddress`를 만들고, [6]단계의 세 주소에서 `TronWeb.isAddress`와 같은 답이 나오는지 확인하세요.

## 🏠 내 생활에서는 <a id="life"></a>

**이 개념이 앱에서 보이는 자리**

- **"받기" 화면**: T로 시작하는 34글자와 QR 코드가 함께 나옵니다. 이 34글자가 오늘 배운 주소입니다.
- **"계정 추가" 메뉴**: 같은 12단어에서 주소를 하나 더 만드는 기능입니다(경로 인덱스만 바뀝니다).
- **"보내기" 화면의 주소 칸**: 글자 하나만 틀려도 앱이 빨간 글씨로 "잘못된 주소"라고 막아 줍니다. 그건 체크섬 4바이트가 하는 일입니다.
- **"복구 구문"·"개인키" 백업 화면**: 여기 나오는 값은 주소가 아니라 열쇠입니다. 화면 캡처도 하지 마세요.
- **주소록(연락처) 기능**: 자주 보내는 주소를 한 번만 정확히 저장해 두면, 다음부터는 붙여 넣기를 하지 않아도 됩니다.

앱은 열쇠를 보관하고, 그 열쇠에서 계산한 주소만 보여 줍니다. 그래서 주소는 친구·거래소·가게에 알려 줘도 됩니다. 반대로 "복구 구문", "개인키", "12단어"를 요구하는 화면이나 사람은 주소가 아니라 열쇠를 달라는 것입니다.

주소를 붙여 넣은 뒤 앞 4글자·뒤 4글자만 맞춰 보는 습관이 있다면 오늘 바꾸세요. 스크립트가 보여 주듯 앞 몇 글자가 같은 "진짜" 주소는 컴퓨터가 얼마든지 만들 수 있고, 앱은 그것을 오타로 잡아 주지 않습니다.

| 이런 요청이 오면 | 사기인가? | 이유 |
|---|---|---|
| 친구가 "사탕 보낼게, 네 T주소 알려 줘" | 아니오 | 주소는 공개해도 되는 값입니다. |
| 거래소 고객센터가 "확인을 위해 12단어를 입력해 주세요" | 예 | 주소가 아니라 열쇠를 달라는 것입니다. 어떤 고객센터도 열쇠를 묻지 않습니다. |
| 거래 내역에 있는 "지난번 보낸 주소"를 복사해 다시 보냄(앞뒤 4글자 확인) | 예(의심) | 앞뒤만 닮은 주소를 내역에 끼워 넣는 주소 오염 사기일 수 있습니다. 전체를 비교하세요. |

**사기 유형 1개 — 주소 오염(address poisoning) (확인 필요: 수법 설명은 일반적으로 알려진 형태)**: 사기꾼이 내가 자주 보내는 주소와 앞뒤 몇 글자가 같은 주소를 만들어 내 지갑에 아주 적은 금액을 보냅니다. 거래 내역에 그 주소가 남고, 다음에 "지난번 주소"를 내역에서 복사하면 사기꾼 주소로 보내게 됩니다. 앱은 체크섬이 멀쩡한 주소를 거부하지 않습니다.

**오늘 실천 습관 1개:** 주소를 보낼 때는 QR 코드나 주소록에 저장한 주소를 쓰고, 붙여 넣은 주소는 앞뒤가 아니라 가운데까지 전체를 눈으로 비교하세요.

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 2. 주소는 모두에게, 열쇠는 아무에게도.**

**해야 할 것**
- ✅ 받을 때는 "받기" 화면의 T주소(또는 QR)를 알려 준다.
- ✅ 보낼 때는 주소 전체를 비교한다. 앞 4·뒤 4만 보지 않는다.
- ✅ 자주 보내는 주소는 주소록에 저장해 두고 그것만 쓴다.

**절대 하지 말 것**
- ❌ 12단어·개인키를 "확인용"으로 입력하지 않는다. 그건 주소가 아니라 열쇠다.
- ❌ 거래 내역에서 주소를 복사해 앞뒤만 보고 보내지 않는다.
- ❌ "주소로 열쇠를 찾아 준다"는 말을 믿지 않는다. 그런 계산은 존재하지 않는다.
