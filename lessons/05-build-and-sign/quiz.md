# Lesson 05 확인 문제 — 편지 쓰고 도장 찍기(아직 안 보내요)

규칙 5: 도장을 찍기 전에 봉투(트랜잭션 내용)를 끝까지 읽는다.

대상별 5문제씩입니다. 정답과 해설은 맨 아래에 있습니다.

---

## 🧒 초등 — 그림·상황 고르기

**초1.** 토리가 봉투에 사탕 수를 잘못 적었어요. 그런데 벌써 도장을 찍었어요. 어떻게 해야 할까요?
① 도장 위에 새 숫자를 덧쓴다
② 새 봉투를 다시 쓴다
③ 여우 씨에게 고쳐 달라고 한다

**초2.** 봉투에 꼭 적어야 하는 세 가지는 무엇일까요?
① 받는 사람, 사탕 수, 유효기간
② 받는 사람, 내 열쇠, 사탕 수
③ 사탕 수, 내 12단어 주문, 유효기간

**초3.** 여우 씨가 "얼른 도장부터 찍어!" 하고 재촉해요. 토리가 해야 할 일은?
① 여우 씨 말대로 빨리 찍는다
② 봉투를 끝까지 읽고 나서 찍는다
③ 여우 씨에게 봉투를 주고 대신 찍어 달라고 한다

**초4.** 토리가 봉투를 쓰고 60초가 지났어요. 아직 우체통엔 안 넣었어요. 무슨 일이 생길까요?
① 사탕이 사라진다
② 아무 일도 안 생긴다. 새 봉투를 쓰면 된다
③ 여우 씨가 사탕을 가져간다

**초5.** 토리의 도장은 어떤 봉투에 맞을까요?
① 아무 봉투에나 다 맞는다
② 도장을 찍은 그 봉투에만 맞는다
③ 여우 씨 봉투에도 맞는다

## 🔍 중고등 — 이유 쓰기

**중1.** 스크립트 출력에서 `txID`는 `[3]`에서 정해지고 `[6]` 서명 뒤에도 그대로였습니다. 그런데 `MEMO`를 붙이면 바뀌었습니다. 왜 서명은 txID를 안 바꾸고 메모는 바꿀까요? 한 문장으로 쓰세요.

**중2.** 이더리움은 nonce(순번)로, 트론은 `ref_block` + `expiration`(60초)으로 "같은 편지 두 번 보내기"를 막습니다. 트론 방식에서 60초를 1시간으로 늘리면 어떤 점이 나빠질지 한 가지 쓰세요.

**중3.** `raw_data_hex`는 133바이트, 서명은 65바이트인데 실제 장부에는 약 266바이트로 기록됩니다(레슨 4의 `net_fee 266000`). 차이 68바이트는 어디서 온다고 추정할 수 있을까요? 그리고 무료 대역폭 600바이트로 하루에 이런 편지를 몇 통까지 덮을 수 있는지 계산 과정을 쓰세요.

**중4.** `extendExpiration(tx, 600)`을 부른 뒤 "반환값이 아니라 입력 객체 `tx`"로 서명하면 왜 실패할까요? 출력의 `입력 객체의 txID … (옛 값 그대로)`, `입력 객체의 expiration … (제자리에서 바뀜)` 두 줄을 근거로 쓰세요.

**중5.** "도장은 종이마다 같은 무늬"라는 비유가 서명에는 왜 맞지 않을까요? 서명이 65바이트의 "값"이라는 점에서 이유를 쓰세요.

## 💻 개발자 — 출력 예측

**개1.** 다음 코드의 출력을 예측하세요.
```js
const a = await tronWeb.trx.sign(tx, pk);
console.log(a === tx, tx.signature?.length);
```

**개2.** 다음 코드의 출력을 예측하세요. (`tx`는 `sendTrx`로 막 만든 미서명 객체)
```js
const { ethers } = require('ethers');
console.log(ethers.sha256('0x' + tx.raw_data_hex).slice(2) === tx.txID);
console.log(tx.raw_data.expiration - tx.raw_data.timestamp);
```

**개3.** 다음 코드는 무엇을 출력할까요? (`signed`는 서명이 끝난 객체)
```js
try {
  await tronWeb.transactionBuilder.addUpdateData(signed, 'memo', 'utf8');
  console.log('ok');
} catch (e) {
  console.log('fail:', errorMessage(e));
}
```

**개4.** 다음 코드의 출력을 예측하세요.
```js
const before = JSON.parse(JSON.stringify(tx));
const ext = await tronWeb.transactionBuilder.extendExpiration(tx, 600);
console.log(ext === tx, ext.txID === before.txID, tx.raw_data.expiration - before.raw_data.expiration);
```

**개5.** 다음 코드의 출력을 예측하세요. (`me.address`는 `TUEZSdKsoDHQMeZwihtdoBiN46zxhGWYdH`)
```js
try {
  await tronWeb.transactionBuilder.sendTrx(me.address, 1000000, me.address);
  console.log('built');
} catch (e) {
  console.log('fail:', errorMessage(e));
}
```

**일1.** 지갑 앱 확인 화면에 받는 주소가 떴는데, 상대가 보낸 주소와 앞 4자·뒤 4자는 같지만 가운데를 비교하지 않았습니다. 확인을 눌러도 될까요? (예/아니오, 이유)

**일2.** 상대가 "60초 안에 확인 안 누르면 거래가 취소돼서 손해예요, 빨리요!"라고 재촉합니다. 어떻게 해야 할까요?
① 손해 보기 전에 빨리 누른다
② 만료돼도 손해가 없으니 천천히 읽고, 다 읽지 못했으면 취소한다
③ 상대에게 대신 눌러 달라고 한다

**일3.** 앱 확인 화면에 내가 입력한 적 없는 금액이 떠 있습니다. 어떻게 해야 할까요?
① 앱이 알아서 계산했겠거니 하고 누른다
② 취소하고, 처음부터 다시 입력해 확인 화면을 다시 읽는다

**일5.** 앱 확인 화면에 "메모"를 적는 칸이 있습니다. 트론 TRX 전송에서 메모를 적으면 무엇이 달라질까요?
① 아무것도 달라지지 않는다

## 정답과 해설

### 초등
- **초1 ②** 도장을 찍은 봉투는 못 고쳐요. 아직 우체통에 안 넣었으니 손해도 없어요. 새 봉투를 쓰면 돼요. 여우 씨에게 맡기면 안 돼요.
- **초2 ①** 열쇠와 12단어 주문은 봉투에 절대 적지 않아요. 봉투에는 받는 사람, 사탕 수, 유효기간을 적어요.
- **초3 ②** 재촉은 봉투를 못 읽게 하려는 속임수예요. 끝까지 읽고 나서 찍어요.
- **초4 ②** 유효기간이 지난 봉투는 우체통이 안 받아요. 사탕은 그대로예요. 새 봉투를 쓰면 돼요.
- **초5 ②** 도장은 그 봉투 내용에 맞춰 찍는 거라 다른 봉투에는 안 맞아요.

### 중고등
- **중1** txID는 봉투 내용(`raw_data_hex`)의 sha256 해시인데, 서명은 내용 바깥(`signature` 필드)에 붙고 메모는 내용 안(`raw_data.data`)에 들어가기 때문입니다.
- **중2** (예시) 같은 봉투를 1시간 동안 다시 낼 수 있게 되어, 잘못 만든 봉투나 유출된 서명본이 오래 살아남습니다. 또는 보내는 사람이 "취소했다"고 생각한 봉투가 한참 뒤에 들어갈 수 있습니다. (출력 근거: `expiration: … (timestamp + 60초)`)
- **중3** 68바이트는 노드끼리 주고받을 때 raw_data와 서명을 감싸는 protobuf(포장 형식) 때문으로 추정합니다(정확한 크기는 확인 필요). 600 ÷ 266 = 2.25…이므로 하루 2통까지는 무료 대역폭으로 덮을 수 있습니다(부분 차감 여부는 확인 필요). 무료 대역폭이 모자라면 1000 sun/byte로 TRX가 소각되는데, 부족분만 차감되는지 전체가 차감되는지는 확인 필요입니다. 정확한 값은 레슨 7의 receipt `net_usage`/`net_fee`로 확인합니다.
- **중4** `extendExpiration`은 입력 객체의 `raw_data.expiration`을 제자리에서 바꾸지만 `txID` 문자열은 옛 값으로 남깁니다. txID는 raw_data의 해시여야 하므로 둘이 어긋난 객체는 유효하지 않고, 서명 시 `Invalid transaction`이 납니다. 반환된 새 객체는 새 txID와 새 raw_data가 일치합니다.
- **중5** 서명은 개인키로 "이 봉투의 txID"에 대해 계산한 65바이트 값이라, 봉투가 다르면 값도 다릅니다. 도장 무늬처럼 베껴서 다른 봉투에 붙여도 그 봉투의 txID와 맞지 않으므로 검증에 실패합니다.

### 개발자
- **개1** `true 1` — `trx.sign`은 입력 객체를 제자리에서 수정하고 같은 객체를 돌려줍니다(expected-output `같은 객체인가 (signed === tx): true`, `서명 후 객체에 signature: 1개`).
- **개2** `true` 그리고 `60000` — txID는 sha256(raw_data_hex)이고, 기본 expiration은 timestamp + 60초(= 60000ms)입니다.
- **개3** `fail: You can not extend the expiration of a signed transaction.` — 메모는 서명 전에만 붙일 수 있습니다. 서명 후 `addUpdateData`를 부르면 tronweb이 이 메시지로 거부합니다.
- **개4** `false false 600000` — 반환값은 새 객체(`ext !== tx`), txID는 바뀌고(`false`), 입력 객체의 expiration은 제자리에서 600초(600000ms) 늘어납니다. (`EXTEND=600 npm run l05` 로 실행하면 `[5]` 에 `입력 객체의 expiration … (제자리에서 바뀜)` 이 나옵니다)
- **개5** `fail: Cannot transfer TRX to the same account` — to와 from이 같으면 tronweb이 빌드 단계에서 예외를 던집니다. 그래서 스크립트는 기본 수신자를 같은 니모닉의 index 1 주소로 둡니다.

### 일반인
- **일1 아니오.** 앞 4자·뒤 4자만 같은 "닮은 주소"가 있을 수 있습니다(레슨 2). 전체를 비교하거나 QR로 받으세요. 봉투를 끝까지 읽는다는 것은 주소도 끝까지 읽는다는 뜻입니다.
- **일2 ②** 트론 봉투는 60초가 지나면 만료되어 아무 일도 일어나지 않습니다. 손해는 없습니다. 재촉은 읽을 틈을 없애려는 수법이니 다 읽지 못했으면 취소하세요.
- **일3 ②** 입력한 적 없는 값이 뜨면 취소가 정답입니다. 복구 구문(12단어)은 어떤 경우에도 누구에게도 알려 주지 않습니다(규칙 1).
- **일4** (예시) 받는 주소·금액·네트워크·수수료 네 칸을 소리 내어 읽고 나서 확인을 눌렀어야 합니다. 확인이 곧 도장이고, 도장 뒤에는 고칠 수 없습니다.
- **일5 ②** 트론 TRX 전송의 메모는 메모 수수료 1 TRX가 추가로 들고, 장부에 그대로 공개됩니다. 개인정보를 적지 마세요. 되돌리기와는 관계없습니다.
