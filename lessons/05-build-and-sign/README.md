## 🔍 원리 들여다보기 <a id="why"></a>

### 비유는 어디까지 맞을까요?

| 이야기 속 비유 | 정식 용어 | 스크립트 출력에서 보이는 자리 |
|---|---|---|
| 봉투 / 편지 | 트랜잭션(transaction) | `[2] 봉투 만들기 — sendTrx 빌드` |
| 받는 사람 칸 | `to_address` | `to_address (hex41): 41b6e7…` |
| 사탕 수 칸 | `amount` (sun) | `amount (sun): 1000000 = 1 TRX` |
| 유효기간 | `expiration` (기본 60초) | `expiration: … (timestamp + 60초)` |
| 최근 장부 참조 | `ref_block_bytes` / `ref_block_hash` | `ref_block_bytes / ref_block_hash: dc4c / 7aa758ebf963d29a` |
| 봉투 번호 | `txID` = sha256(raw_data_hex) | `[3] … txID === sha256(raw_data_hex)` |
| 도장 | 서명(signature, 65바이트) | `[6] … signature[0]: … (130 hex = 65 bytes)` |
| 우체통에 넣기 | 브로드캐스트(sendRawTransaction) | 이 레슨에서는 **호출하지 않음** |

### 실험 1: 출력에서 한 줄 찾기 — 봉투는 몇 바이트일까요?

스크립트를 실행하고 `[2]` 단계에서 다음 줄을 찾습니다.

```
  raw_data_hex 크기: 133 bytes
```

봉투 내용(raw_data)만 133바이트입니다. 여기에 도장 65바이트가 붙습니다. 계산해 봅시다.

- 133 + 65 = 198바이트. 그런데 레슨 4에서 본 실제 영수증의 `net_fee`는 266000 sun, 즉 266바이트분이었습니다.
- 차이 68바이트는 노드끼리 주고받을 때 씌우는 protobuf(노드끼리 쓰는 포장 형식) 때문으로 **추정**합니다. 포장의 정확한 크기는 확인 필요이며, 실제 값은 영수증의 `net_usage`/`net_fee`로 확인합니다.
- 무료 대역폭은 하루 600바이트입니다. 266바이트짜리 편지라면 600 ÷ 266 = 2.25…, 즉 **2통**까지 덮입니다.
- 무료 대역폭이 모자라면 1000 sun/byte로 TRX가 소각됩니다. 부족분만 차감되는지 전체가 차감되는지는 **확인 필요**이므로, 정확한 정산은 레슨 7에서 영수증으로 봅니다.

### 실험 2: 환경변수 바꿔 보기 — 메모 한 글자가 봉투 번호를 바꿉니다

```bash
MEMO="hi" npm run l05
```

`[4]` 단계에서 `txID 전`과 `txID 후`가 다른 값으로 나옵니다. 한 번 더 `MEMO="hi!"`로 실행하면 또 다른 값입니다. 봉투 번호(txID)는 내용의 sha256 해시라서, 내용이 1비트만 달라도 64자리 hex(= 32바이트 = 256비트)가 전부 바뀝니다. 가능한 번호의 수는 2^256개입니다.

이어서 `EXTEND=600 npm run l05`를 실행해 보세요. `[5]` 단계에서 유효기간이 600초 늘어나면서 역시 txID가 바뀝니다. **유효기간도 봉투 내용의 일부**이기 때문입니다.

### 왜 그렇게 설계했을까요?

> 이더리움은 계정마다 번호표(nonce)를 붙여 "같은 편지를 두 번 보내기"를 막습니다. 트론은 번호표 대신 **"어느 장(ref_block)을 보고 썼는지"와 "언제까지 유효한지(expiration)"** 를 봉투에 적습니다. 번호표가 없으면 편지를 순서 없이 여러 통 동시에 낼 수 있어 편리하지만, 대신 60초 안에 우체통에 넣어야 합니다. 어느 쪽이 "실수로 두 번 보내기"를 더 잘 막을까요? 60초를 6000초로 늘리면 무엇이 나빠질까요?

### 비유의 한계 한 줄

편지는 나중에 내용을 고칠 수 있지만, 봉투 번호(txID)는 내용의 해시라서 한 글자만 바꿔도 **새 봉투**가 됩니다. 도장도 종이마다 같은 무늬가 아니라 **봉투마다 다른 값**이라, 도장을 베껴도 다른 봉투에는 못 씁니다.

### [1/7]·[2/7] 봉투 만들기 — 미서명 트랜잭션

```
  보내는 사람(from, index 0): TUEZSdKsoDHQMeZwihtdoBiN46zxhGWYdH
  받는 사람(to, 같은 니모닉 index 1): TSeJkUh4Qv67VNFwY8LaAxERygNdy6NQZK
  amount (sun): 1000000 = 1 TRX
  expiration: 1789224669000 = 2026-09-12T14:51:09.000Z (timestamp + 60초)
  raw_data_hex 크기: 133 bytes
  signature: (없음 — 아직 도장을 안 찍었습니다)
```

`transactionBuilder.sendTrx(toT, amountSun, fromT)`는 노드에서 최근 블록을 읽어 `ref_block_*`을 채운 **미서명** 객체를 돌려줍니다. raw_data 안 주소는 `41`+40hex이며 스크립트가 T주소를 함께 보여 줍니다. 수신자를 index 1로 두는 이유는 `to === from`이면 tronweb이 `Cannot transfer TRX to the same account` 예외를 던지기 때문입니다.

### [3/7] txID는 서명 전에 정해진다

```
  txID (노드가 준 값): 15a4060a09a8a4f5c1b3477f09f50caa78c9bf8f7417ce53c6020255dc9eba91
  sha256(raw_data_hex) (직접 계산): 15a4060a09a8a4f5c1b3477f09f50caa78c9bf8f7417ce53c6020255dc9eba91
  ✅ 일치합니다. txID 는 서명이 아니라 봉투 내용의 해시입니다.
```

```js
const computed = ethers.sha256('0x' + tx.raw_data_hex).slice(2); // === tx.txID
```

이더리움의 tx hash는 서명까지 포함한 RLP의 keccak256이지만(확인 필요), 트론의 txID는 **서명 전** `raw_data`의 sha256입니다. 그래서 오프라인에서 도장을 찍기 전에 이미 "나중에 영수증을 찾을 번호"를 알 수 있습니다(레슨 7).

### [4/7]·[5/7] 메모와 유효기간 — 둘 다 서명 전에만

`MEMO`를 주면 `addUpdateData(tx, memo, 'utf8')`가 `raw_data.data`(hex)를 붙인 **새 객체**를 돌려주고 txID가 바뀝니다. 서명 뒤에 부르면 tronweb이 `You can not extend the expiration of a signed transaction.` 으로 거부합니다. 체인 파라미터 `getMemoFee`가 1,000,000 sun이므로 메모 한 줄에 1 TRX가 추가로 소각됩니다.

```js
const original = snapshot(tx); // JSON.parse(JSON.stringify(tx))
const extended = await tronWeb.transactionBuilder.extendExpiration(tx, extend);
// tx.raw_data.expiration 은 이미 바뀌었지만 tx.txID 는 옛 값 → tx 는 더 이상 쓰면 안 됨
tx = extended;
```

### [6/7] 서명 — 오프라인, 입력 객체를 바꾼다

```
  signature[0]: d493441657bee1c3… (130 hex = 65 bytes)
  같은 객체인가 (signed === tx): true
  txID 변화: 없음 (서명은 txID 를 바꾸지 않는다)
  서명 후 객체에 signature: 1개
```

`trx.sign(tx, pkHexWithout0x)`은 노드에 접속하지 않습니다(에어갭 운용 절차 자체는 확인 필요). 반환값은 입력과 **같은 객체**이고, `signature: ['130hex']`만 추가됩니다. 다른 사람 키로 서명하면 노드까지 가지 않고 `Private key does not match address in transaction` 예외가 납니다.

### [7/7] 파일로 저장 — 우체통에는 넣지 않는다

`out/05-signed.json`(1097 bytes)은 `sendRawTransaction`에 그대로 넘길 수 있는 형태입니다. 다만 60초가 지나면 만료되어 노드가 받지 않으므로 레슨 6은 이 파일을 재사용하지 않고 처음부터 다시 빌드합니다. `out/`은 `.gitignore`에 들어 있어 커밋되지 않습니다.

### 트론 vs EVM 차이 박스

| 항목 | TRON (Nile) | EVM (BTTC Donau) |
|---|---|---|
| 중복·재생 방지 | `ref_block_bytes`/`ref_block_hash` + `expiration`(기본 60초) | 계정별 `nonce`(확인 필요) |
| 트랜잭션 ID | `sha256(raw_data_hex)`, **서명 전** 확정 | 서명까지 포함한 해시(확인 필요) |
| 주소 표기(raw) | `41` + 40hex | `0x` + 40hex (같은 20바이트) |
| 수수료 지정 | 단순 전송은 대역폭 소모, 컨트랙트는 `fee_limit`(sun 정수) | `gasLimit` × `gasPrice` (Donau는 legacy gas) |

### 함정 1개: "제자리 수정" 두 가지

`trx.sign`과 `extendExpiration`은 둘 다 입력 객체를 바꾸는데 방향이 다릅니다. `sign`은 바꾼 **그 객체**를 돌려주니 반환값과 입력이 같지만, `extendExpiration`은 입력의 `raw_data`만 고치고 **새 txID를 가진 다른 객체**를 돌려줍니다. 입력 객체를 계속 쓰면 `raw_data`와 `txID`가 어긋나 서명 시 `Invalid transaction`이 납니다. 규칙은 하나입니다. **반환값만 쓰고, "전" 모습이 필요하면 미리 JSON 복사.**

### 도전

- **쉬움**: `EXTEND=600 npm run l05`를 실행해 `[5]`의 "입력 객체의 txID"와 "입력 객체의 expiration" 두 줄을 읽고, 왜 하나는 "옛 값 그대로"이고 다른 하나는 "제자리에서 바뀜"인지 한 줄로 적어 보세요.
- **어려움**: `out/05-signed.json`을 읽어 (1) `txID === sha256(raw_data_hex)`, (2) `expiration`이 현재 시각보다 뒤, (3) `signature[0]`이 130 hex인지 검사하는 `verify-envelope.js`를 만들어 보세요. 세 가지가 다 통과해야 "우체통에 넣을 수 있는 봉투"입니다. 서명자 복원도 붙여 보세요. 서명은 txID 32바이트에 대한 것이라 `ethers.recoverAddress('0x' + signed.txID, '0x' + signed.signature[0])` → `0xC8599111F29c1e1E061265b4AF93eA1F274aD78A` → `'41' + 그 hex` → `TUEZSdKsoDHQMeZwihtdoBiN46zxhGWYdH`, 즉 `owner_address`와 같은 주소가 복원됩니다(검증됨).

## 🏠 내 생활에서는 <a id="life"></a>

지갑 앱(TronLink 등)에서 "보내기"를 누른 뒤 나오는 **확인 화면**이 바로 이 레슨의 봉투입니다. 화면에는 받는 주소, 금액, 네트워크(TRON), 예상 수수료(대역폭·에너지 또는 소각될 TRX)가 있습니다(앱마다 화면 구성은 다를 수 있음, 확인 필요).

"확인"을 누르는 순간이 도장(서명)이고, 그 뒤 앱이 알아서 우체통에 넣습니다(브로드캐스트). 그러니 **"확인"을 누르기 전이 봉투를 읽을 마지막 기회**입니다. 받는 주소는 앞 4자·뒤 4자만이 아니라 전체를, 금액은 단위(TRX인지 USDT인지)까지, 네트워크는 상대가 말한 것과 글자까지 맞춰 읽으세요.

| 이런 요청이 오면 | 사기인가? | 이유 |
|---|---|---|
| 앱 확인 화면에 받는 주소·금액·수수료가 보이고, 내가 입력한 것과 같다 | 아니오 | 정상적인 봉투 읽기 단계입니다. 읽고 나서 확인하세요. |
| "시간이 없어요, 60초 안에 확인 안 누르면 손해예요"라며 재촉한다 | 예 | 만료되면 새로 만들면 됩니다. 재촉은 봉투를 못 읽게 하려는 수법입니다. |
| 내가 입력한 적 없는 주소나 금액이 확인 화면에 떠 있다 | 예(의심) | 복사·붙여넣기 과정에서 주소가 바뀌었거나 악성 앱입니다. 취소하세요. |

확인 화면에 "메모"나 "태그" 칸이 보이면 비워 두세요. 트론 TRX 전송에서 메모를 적으면 수수료 1 TRX가 더 들고, 적은 내용이 장부에 그대로 공개됩니다. 이름, 전화번호, 주문번호 같은 개인정보는 적지 마세요.

**사기 유형 1개 — 재촉형 블라인드 서명.** "지금 당장 확인 눌러야 해요", "읽을 필요 없어요, 제가 다 확인했어요"라며 확인 화면을 읽을 틈을 주지 않습니다. 트론 봉투는 60초가 지나면 만료되어 아무 일도 일어나지 않으므로, 늦어서 손해 볼 일은 없습니다. 읽지 못했으면 취소하세요.

**오늘 실천 습관 1개:** 다음에 앱에서 "확인"을 누르기 전에 받는 주소, 금액, 네트워크, 수수료 네 가지를 **소리 내어** 읽어 보세요. 오늘 연습은 실제 지갑이 아니라 [서명 팝업 판별 놀이](../../playground/signing-popup-simulator.html)에서 하세요 — 브라우저로 열고 네 칸을 읽는 연습만 하면 됩니다. 실제 지갑의 보내기 화면은 정말 보낼 일이 생겼을 때 열고, 그때 네 가지를 소리 내어 읽으세요.

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 5. 도장을 찍기 전에 봉투(트랜잭션 내용)를 끝까지 읽는다.**

**해야 할 것**
- ✅ 받는 주소·금액·네트워크·수수료, 네 칸을 모두 읽고 나서 확인을 누른다.
- ✅ 하나라도 다르면 취소하고 새 봉투를 만든다. 만료(60초)는 손해가 아니다.
- ✅ 서명한 봉투는 못 고친다는 걸 기억하고, 서명 전에 고친다.

**절대 하지 말 것**
- ❌ "빨리 눌러요"라는 말에 안 읽고 확인 누르기.
- ❌ 남이 대신 읽어 줬다고 믿고 확인 누르기.
- ❌ 내용을 모르는 봉투(hex만 있는 요청)에 서명하기.
