## 🧒 이야기로 시작 <a id="story"></a>

토리가 앱을 보며 사탕 수를 세어요.
"아저씨, 내 사탕은 여기 적혀 있죠?"
"앱이 하는 말 말고, 장부엔 뭐라고 적혀 있니?"

둘은 누구나 볼 수 있는 광장 장부(블록체인) 앞에 서요.
"사탕상자 1개는 사탕 100만 알이란다."
톡, 3초마다 새 장이 붙어요.

그때 여우 씨가 사탕통을 들고 와요.
"이거 진짜 사탕이야, 이름이 똑같잖아!"
아저씨가 사탕통 번호를 짚어요.
"번호가 다르네, 이름은 누구나 붙여."

여우 씨가 물러가자 아저씨가 낡은 상자를 가리켜요.
"이 상자는 열쇠 구멍 주인이 다른 사람이네. 왜인지는 나중에."

**핵심 한 문장:** 잔고는 앱이 아니라 장부(탐색기)에서 확인하고, 토큰은 이름이 아니라 컨트랙트 주소로 알아본다.

**엄마 아빠에게 물어보기:** "이름이 똑같은 물건이 두 개 있으면 어떻게 진짜를 알아보나요?"

### 실험 1: 출력에서 한 줄 찾기 — 왜 sun으로 셀까요?

스크립트를 실행하고 `[2]`에서 `잔고 (sun): 55,167,408,590 sun` 과 `잔고 (TRX): 55167.40859 TRX` 두 줄을 찾습니다. 55,167,408,590 ÷ 1,000,000 = 55,167.40859. 나누는 수는 10^6이고 소수점이 정확히 여섯 자리 왼쪽으로 갑니다. 체인은 언제나 정수(sun)로 기록하고 사람에게 보여 줄 때만 나눕니다. 소수 계산의 오차를 없애기 위해서입니다.

`[4]`에서도 같은 구조를 찾아보세요. `balanceOf (최소 단위): 19,589,654,444` 와 `19589.654444 USDT`. USDT의 decimals가 6이라 역시 10^6으로 나눕니다. 다만 TRX는 체인이 직접 세고 USDT는 컨트랙트 안의 표가 셉니다. 장부가 둘입니다.

### 왜 그렇게 설계했을까요?

왜 잔고를 지갑 앱이 저장하지 않고, 앱은 매번 체인에 물어볼까요? 앱 회사가 문을 닫아도, 휴대폰을 잃어버려도 잔고는 장부에 그대로 남아 있어야 하기 때문입니다. 앱은 창문이고 장부가 방입니다. 창문이 깨져도 방 안 물건은 그대로입니다. 그러면 반대로, 창문이 잘못된 숫자를 보여 줄 수도 있을까요? 그래서 규칙 3이 있습니다.

### 비유의 한계

장부는 한 권이지만 블록체인은 장부지기(노드)마다 한 권씩이고 서로 맞춰 보는 것입니다. 사탕은 반으로 못 쪼개지만 sun이 최소 단위라서 사탕상자 1개는 100만 알까지만 나뉩니다.

### [1/6] 최신·확정 블록과 [2/6] getBalance

```
  최신 블록 번호: 70,900,868 (2026. 9. 12. 오후 11:52:57)
  확정 블록 번호: 70,900,849 (2026. 9. 12. 오후 11:52:00)
  잔고 (sun): 55,167,408,590 sun
  잔고 (TRX): 55167.40859 TRX
```

`getCurrentBlock()`은 최신, `getConfirmedCurrentBlock()`은 확정(solidified) 블록입니다. 19블록 차이에 시각 차이가 57초, 즉 블록당 약 3초이고, 잔고를 믿을 기준은 확정 블록입니다. `getBalance(addr)`는 sun 을 number 로 돌려주며 `lib/tron.js` 의 `sunToTrx` 가 `TronWeb.fromSun` 의 BigNumber 를 문자열로 바꿉니다. 계산은 정수로, 나누기는 표시할 때만.

### [3/6] getAccount — 활성화, 스테이킹, TRC-10

```
  ✅ 활성화된 계정입니다 (장부에 이 주소의 장이 있습니다).
  맡긴 TRX (frozenV2): BANDWIDTH=17949 TRX, ENERGY=17950 TRX, TRON_POWER=0 TRX
  TRC-10 #1005416: TRN (TN) 300 개 — precision 6
```

활성화된 계정이면 객체가, 아니면 **빈 객체 `{}`** 가 옵니다(`Object.keys(account).length > 0` 으로 판정). `frozenV2` 는 Stake 2.0, `assetV2` 는 TRC-10 이고 이름은 `getTokenFromID` 로 조회해 `precision` 을 적용합니다. `type` 이 없는 첫 항목을 대역폭으로 적는 것은 관례입니다(확인 필요: 사실 문서에서 확인되지 않음).

### [4/6] TRC-20 별도 장부와 [5/6] 가짜 토큰 경고

```
  체인에 기록된 컨트랙트 이름: TetherToken (ABI 항목 46개)
  balanceOf (최소 단위): 19,589,654,444
  바꿀 수 없는 것: 컨트랙트 주소. 이 강의가 쓰는 Nile 의 USDT 는 TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf 입니다.
  ⚠️  같은 이름 "USDT" 라도 컨트랙트 주소가 다르면 완전히 다른 토큰입니다. 받은 토큰의 주소를 꼭 확인하세요.
```

`getContract(addr)` 는 체인에 적힌 이름과 ABI 항목 수를, `tronWeb.contract(TRC20_ABI, NILE.usdt).balanceOf(address).call()` 은 uint256 잔고를 돌려줍니다(`BigInt` 로 받아 `formatUnits(raw, decimals)`). `tronweb.contract` 는 JSON ABI 객체 배열만 받습니다. TRX 와 USDT 는 다른 장부이고, `name()`/`symbol()` 은 컨트랙트가 정한 문자열이라 토큰의 신원은 컨트랙트 주소뿐입니다. 화이트리스트도 주소로 관리하세요.

### [6/6] 계정 권한

```
  owner_permission.keys[0].address: 41156f4463ce90ac11e1855ff99e4273806ad847cf
  내 hex 주소: 41c8599111f29c1e1e061265b4af93ea1f274ad78a

```

정상 계정은 `owner_permission.keys[0].address === 계정 hex 주소`입니다. 데모 니모닉이 공개된 값이라 누군가 권한을 자기 키로 바꿔 두었고, 개인키가 있어도 전송이 안 됩니다(조회·시뮬레이션은 가능). Lesson 13 점검이 여기서 시작됩니다.

### 트론 vs EVM 차이

| | 트론(Nile) | EVM(BTTC Donau 등) |
|---|---|---|
| 잔고 최소 단위 | sun (10^6 = 1 TRX) | wei (10^18 = 1 BTT/ETH) |
| 잔고 조회 | `tronWeb.trx.getBalance(T주소)` → number | `provider.getBalance(0x주소)` → bigint |
| "계정 없음" 표현 | `getAccount` → `{}` (활성화 개념 있음) | 잔고 0, nonce 0 (활성화 개념 없음) |
| 계정 권한 변경 | owner/active permission 변경 가능 | 없음(EOA 키 고정) (확인 필요) |
| 확정 블록 조회 | `getConfirmedCurrentBlock()` | `getBlock('finalized')` (확인 필요) |

### 함정 1개: 컨트랙트 `.call()`에도 "묻는 사람" 주소가 필요하다

`.balanceOf(x).call()` 은 내부적으로 `triggerConstantContract` 를 호출해 `owner_address` 를 요구합니다. 등록된 주소가 없으면 노드가 `class java.security.InvalidParameterException : owner_address isn't set.` 예외를 돌려줍니다. 읽기 전용인 이 레슨은 개인키 없이 `tronWeb.setAddress(address)` 로 주소만 등록하고, 서명이 필요한 레슨은 `createTronWeb(privateKey)` 를 씁니다.

### 도전 2개

- **쉬움:** `[3]` 의 TRC-10 출력을 `assetV2` 전체 표로 확장하세요(`getTokenFromID` 는 토큰마다 호출되니 `tryCall` 로 감싸 429에 대비).
- **어려움:** 같은 니모닉 index 0~4 주소 5개(Lesson 02)를 조회해 `주소 / 활성화 / TRX / USDT / 권한 키 = 나?` 표를 출력하고, 미활성화 주소의 `balanceOf` 가 0인지 예외인지 주석으로 남기세요.

## 🏠 내 생활에서는 <a id="life"></a>

지갑 앱(TronLink 등)의 자산 목록에 TRX와 USDT가 나란히 보입니다. 하지만 그 숫자는 앱이 체인에 물어본 결과를 옮겨 적은 것입니다. 앱이 잠시 못 불러오면 0으로 보일 수도 있고, 가짜 토큰이 "USDT"라는 이름으로 끼어들 수도 있습니다. 진짜 잔고는 탐색기에서 확인하세요.

- **탐색기에서 내 주소 검색:** https://nile.tronscan.org 에서 내 T주소를 검색하면 TRX 잔고와 토큰 목록이 나옵니다(연습 나라 기준. 진짜 나라는 탐색기 주소가 다릅니다). 앱 잔고와 숫자가 같은지 대조하세요.
- **토큰은 컨트랙트 주소로:** 앱에서 토큰을 눌러 컨트랙트 주소를 확인하세요(메뉴 위치는 앱마다 다름, 확인 필요). 이 강의가 쓰는 Nile의 USDT는 `TXYZopYRdj2D9XRtbG411XZZ3kM5VkAeBf` 입니다. 이름이 같은 다른 컨트랙트는 다른 토큰입니다.
- **앱에서 이 개념이 보이는 자리:** 자산 목록의 TRX 숫자는 체인의 `getBalance` 값을, 토큰 줄의 숫자는 그 토큰 컨트랙트의 `balanceOf` 값을 옮겨 적은 것입니다. 두 숫자는 출처가 다릅니다.
- **탐색기 토큰 탭:** 탐색기에서 내 주소를 열면 TRX 잔고와 토큰 목록이 따로 보입니다. 토큰 줄을 눌러 컨트랙트 주소까지 확인하는 것이 규칙 3의 실천입니다.
- **모르는 토큰은 만지지 마세요:** 갑자기 들어온 토큰은 그냥 두세요. 눌러서 무언가를 승인하는 순간 서명 요청이 따라옵니다.

**이런 요청이 오면 사기인가?**

| 상황 | 사기? | 이유 |
|---|---|---|
| "앱이 잔고를 못 불러와요. 이 번호로 전화해서 복구 구문을 알려 주세요." | 예 | 잔고는 장부에 있어서 앱이 못 불러와도 사라지지 않습니다. 복구 구문을 묻는 순간 사기입니다. |
| 지갑에 이름이 "USDT"인 토큰이 갑자기 들어왔는데 컨트랙트 주소가 다릅니다. | 예 | 이름은 누구나 붙일 수 있습니다. 주소가 다르면 다른 토큰이고, 보통 서명 유도용 미끼입니다. |
| 앱 잔고와 탐색기(nile.tronscan.org) 잔고가 같습니다. | 아니오 | 장부와 앱이 일치하는 정상 상태입니다. 이 확인을 습관으로 하세요. |

**사기 유형 1개 — 가짜 토큰 에어드랍:** 이름·심볼·로고까지 진짜와 똑같이 만든 토큰을 아무 지갑에나 뿌립니다. 지갑 앱에 "USDT 1,000"처럼 보이니 그 토큰을 눌러 무언가를 승인하면, 그 토큰 컨트랙트가 서명을 요구하고 진짜 자산에 손을 댑니다. 방어는 하나입니다. 컨트랙트 주소가 다르면 없는 셈 치세요.

**오늘 실천 습관 1개:** 지갑 앱을 열 때 탐색기도 같이 열어 내 주소를 검색하고, TRX·USDT 숫자가 같은지 한 번 대조하세요. 한 달에 한 번이면 충분합니다.

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 3. 잔고는 앱이 아니라 장부(탐색기)에서 확인하고, 토큰은 이름이 아니라 컨트랙트 주소로 알아본다.**

**해야 할 것**
- ✅ 잔고는 탐색기(장부)에서 내 주소를 검색해 확인한다.
- ✅ 토큰은 이름이 아니라 컨트랙트 주소로 알아본다.
- ✅ 사탕상자 1개 = 사탕 100만 알. 앱이 보여 주는 소수는 장부의 정수를 나눈 것이다.

**절대 하지 말 것**
- ❌ 앱 잔고만 믿고 "입금 확인"이라고 말하지 않는다.
- ❌ 갑자기 들어온 모르는 토큰은 누르지 않는다.
- ❌ "잔고를 못 불러온다"는 이유로 복구 구문을 알려 주지 않는다.
