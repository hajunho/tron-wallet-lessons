### 비유 → 정식 용어

| 비유 | 정식 용어 | 코드에서 보이는 자리 |
|---|---|---|
| 반송 도장 | 에러 메시지 (예외 문자열 또는 `{ code, message(hex) }`) | 각 사건의 `단서(예외)` 줄 |
| 내 컴퓨터가 먼저 찍는 도장 | tronweb/ethers가 노드에 보내기 전에 던지는 예외 | 사건 1·2·5 |
| 장부지기가 찍는 도장 | 노드·컨트랙트 응답 | 사건 3(`CONTRACT_VALIDATE_ERROR`), 사건 4(`REVERT`) |
| 장부에 이름이 없는 새 상자 | 미활성화 계정 (`getAccount` → `{}`) | 사건 3 |
| 우체통 앞 마지막 확인 | 관문 (`lib/guard.js`의 `assertCanSend`) | 사건 3 |
| 유효기간 | `expiration` (기본 `timestamp` + 60초) | 사건 7 |
| 열쇠 구멍 주인 | `owner_permission.keys[0].address` | 사건 9 |

### 실험 1 — 사건 3에서 "어디까지 갔는지" 한 줄 찾기

`npm run l12`를 실행하고 사건 3의 `getAccount(새 지갑)` 줄이 `{}`인 것을 확인하세요. 그 아래 `빌드`와 `서명` 줄은 성공합니다. 빌드·서명은 내 컴퓨터 안에서 끝나는 계산이라, 계정이 장부에 있든 없든 됩니다. 그다음 줄에서 관문이 막습니다: `SEND_TX=false (기본값) 이므로 … 보내지 않습니다`. 즉 이 레슨은 "봉투는 완성됐지만 우체통에는 넣지 않는" 지점에서 멈춥니다. 이 봉투를 실제로 넣으면 노드가 `CONTRACT_VALIDATE_ERROR / account [T…] does not exist`로 돌려준다는 것은 2026-09-12에 잔고 0 새 지갑으로 관찰해 둔 기록입니다.

### 실험 2 — 사건 7에서 유효기간을 숫자로 보기

`CASE=7 npm run l12`로 사건 7만 실행하세요. `timestamp`와 `expiration`의 차가 정확히 60초입니다. 트론에는 nonce가 없어서, 같은 봉투가 나중에 다시 쓰이는 것을 최근 블록 참조(`ref_block`)와 이 60초로 막습니다. 그다음 `extendExpiration(복사본, 600)`을 부르면 유효기간이 660초로 늘고 `원래 txID`와 `연장된 txID`가 완전히 달라집니다. 만료 시각도 봉투 내용(`raw_data`)의 일부라서 해시가 바뀌는 것입니다(레슨 5). 그래서 연장은 반드시 서명 전에 하고, 반환값의 txID만 씁니다. 실제로 만료된 봉투를 넣었을 때 노드가 어떤 문구를 주는지는 이 레슨에서 확인하지 않았습니다(확인 필요).

### 실험 3 — 환경변수 바꿔 보기

- `CASE=4 LEVEL=teen npm run l12` — 💬 해설이 중고등용으로 바뀝니다. `보내려는 양(raw)`이 `잔고 + 1`, 곧 0.000001 USDT 차이인데도 컨트랙트가 되돌립니다. 잔고 값은 실행 시점마다 달라집니다.
- `CASE=10 npm run l12` — `CASE 는 1~9 사이의 숫자여야 합니다`로 exit 1. 이것도 "내 컴퓨터가 먼저 찍는 도장"입니다.

### 실험 4 — 파랑 도장과 빨강 도장을 출력에서 가려내기

`CASE=1 npm run l12` 부터 `CASE=9 npm run l12` 까지 하나씩 돌리면서, 각 사건의 "단서" 줄이 **어디서 찍혔는지**만 적어 보세요. 기준은 하나입니다. 출력에 노드 응답(`{ code: ... }`)이나 `REVERT` 가 등장하면 광장까지 갔다는 뜻이고, 그런 줄 없이 예외 문구만 있으면 내 컴퓨터(tronweb)가 먼저 걸렀다는 뜻입니다.

| 사건 | 단서를 찍은 곳 | 카드 테두리 색 | 수수료 |
|---|---|---|---|
| 1 주소 오타 | 내 컴퓨터 | 파랑 | 0 |
| 2 자기 자신에게 | 내 컴퓨터 | 파랑 | 0 |
| 3 미활성화 계정 | 노드(검증 단계) | 빨강 | 0 (검증에서 거부돼 장부에 오르지 않음) |
| 4 토큰 잔고 초과 | 노드(리허설) | 빨강 | 0 (이 레슨은 리허설로만 확인) |
| 5 다른 키로 서명 | 내 컴퓨터 | 파랑 | 0 |
| 6~9 | 출력을 보고 직접 채우기 | | |

표를 채우고 나면 "빨강이라고 다 수수료가 나가는 건 아니다"라는 것이 보입니다. 수수료가 실제로 나가는 것은 **장부에 올라간 뒤 실패한 경우**(전송 후 REVERT)뿐이고, 이 레슨에서는 그 상황을 만들지 않습니다.

### 왜 그렇게 설계했을까요?

트론은 왜 실패를 두 단계로 나눠 알려 줄까요? 주소 오타(사건 1)나 키 불일치(사건 5)는 노드에 물어볼 필요가 없으니 라이브러리가 즉시 거릅니다. 반면 "계정이 활성화됐나"(사건 3), "컨트랙트가 허락하나"(사건 4)는 장부 상태를 봐야 하니 노드가 답합니다. 즉시 거르는 실패는 수수료가 0이고 재시도가 쉽습니다. 장부에 올라간 뒤의 실패(REVERT)는 수수료를 냅니다. 그래서 레슨 10의 리허설이 먼저이고, 이 레슨의 사건 4도 리허설로 확인합니다.

### 비유의 한계

반송 도장은 우체국(노드)이 찍지만, 사건 1·2·5의 도장은 우체국까지 가기도 전에 내 컴퓨터(tronweb)가 찍습니다. 그리고 진짜 우편은 반송되면 편지를 돌려받지만, 장부에 올라간 뒤 REVERT 된 봉투는 수수료를 돌려주지 않습니다.

```bash
npm run l12                 # 9개 사건 모두 (약 4초)

LEVEL=kid npm run l12       # 💬 해설을 초등용으로
```

MNEMONIC이 없으면 데모 니모닉으로 실행됩니다. 사건 3만 봉투를 실제로 빌드·서명하고, 브로드캐스트 직전에 `lib/guard.js`의 `assertCanSend`를 거칩니다. `SEND_TX=false`(기본)면 사건 3은 그 관문에서 멈추고 빌드·서명까지만 보여 줍니다. 나머지 여덟 사건은 조회·리허설·오프라인 계산뿐입니다.

### 사건 3만 자세히 — 봉투는 완성되고, 관문에서 멈춘다

[4] 사건 3 · 미활성화 계정에서 보내기 — 새 지갑이라 장부에 없어요 (빌드·서명 → 관문)

  ⚠️  SEND_TX=false (기본값) 이므로 미활성화 계정 전송 실험을(를) 보내지 않습니다. …
  ✅ 관문에서 멈췄습니다. 빌드·서명까지만 했고 우체통(노드)에는 넣지 않았습니다. 자산 이동 없음.

```js
const signed = await tronWeb.trx.sign(tx, strangerPk);    // 여기까지는 모두 오프라인
let gatePassed = false;
try {
  await assertCanSend({ mnemonic, what: '미활성화 계정 전송 실험' }); // 브로드캐스트 직전 관문
  gatePassed = true;
} catch (error) {
  if (!(error instanceof GuardError)) throw error;         // GuardError 는 정상 흐름(exit 0)
  print.warn(error.message);
}
if (gatePassed) await tronWeb.trx.sendRawTransaction(signed);
```

관문을 통과했을 때만 브로드캐스트합니다. `sendRawTransaction`은 실패해도 예외를 던지지 않고 `{ code, message }`를 돌려주며, `message`는 hex라서 `lib/tron.js`의 `decodeNodeMessage`로 읽습니다.

### 트론 vs EVM 차이

| | 트론 (Nile, tronweb) | EVM (BTTC, ethers) |
|---|---|---|
| 자기 자신에게 전송 | 빌드 단계에서 예외 | 허용됨(가스만 소모, 확인 필요) |
| 새 계정 | TRX를 받아 "활성화"해야 보낼 수 있음(`does not exist`) | 별도 활성화 없음(확인 필요) |
| 실패 응답 형태 | 예외(문자열일 수도) 또는 `{ code, message(hex) }` | `Error { shortMessage, code, info }` |
| 재사용 방지 | `ref_block` + `expiration`(60초), nonce 없음 | nonce |
| 권한 | owner/active 권한을 다른 키로 바꿀 수 있음 | 외부 계정은 키 = 계정, 권한 변경 없음(확인 필요) |
| 잔고 부족 | 컨트랙트 `REVERT` / 노드 검증 오류 | `estimateGas`에서 `insufficient funds` |

### 함정 1개

tronweb의 예외는 **`Error` 객체가 아니라 문자열**일 때가 있습니다(예: `contract.transfer().send()`의 `Contract validate error : …`). `error.message`만 찍으면 `undefined`가 나옵니다. 이 저장소는 `errorMessage(error)`로 문자열·객체·`shortMessage`를 모두 받아 냅니다. 한 가지 더: 에러 문구에는 주소·hex·가스 숫자가 섞여 들어옵니다(예: 사건 8의 `supplied gas 10010499`). 그래서 "네트워크 오류인지"를 문구 속 `429`·`502` 같은 숫자로 판별하면 예상한 단서를 네트워크 오류로 오분류할 수 있습니다. 이 스크립트는 `error.code`와 HTTP status로 먼저 판별하고, 문자열 매칭은 `Too Many Requests`처럼 겹칠 수 없는 문구로만 좁혔습니다.

### 도전

- **쉬움**: 사건 6의 `ZERO_TXID`를 레슨 7에서 봤던 실제 txID(`dd46b445…c8bd8`)로 바꿔 `getTransactionInfo`가 `{}`가 아닌 영수증을 돌려주는지 확인하세요. `TXID` 환경변수를 새로 받도록 고쳐 보세요.
- **어려움**: 사건 3의 새 지갑을 재사용할 수 있게 고쳐, 활성화 뒤에 `CONTRACT_VALIDATE_ERROR`가 사라지는지 보세요. ① `SHOW_SECRETS=true CASE=3 npm run l12`로 새 지갑의 주소와 개인키를 적어 둡니다(스크립트가 실행마다 `TronWeb.createRandom()`으로 새로 만들기 때문에, 적어 두지 않으면 다음 실행에서 또 다른 주소가 생깁니다). ② Nile faucet(`https://nileex.io/join/getJoinPage`)으로 그 주소에 TRX를 받습니다. ③ `stranger` 자리를 `process.env.STRANGER_PK`가 있으면 그 키를 쓰도록 레슨 안의 지역 코드로 고칩니다(`lib/`는 건드리지 않습니다). ④ `STRANGER_PK=… CASE=3 SEND_TX=true npm run l12`로 다시 돌립니다. 브로드캐스트 직전 `assertCanSend`는 그대로 두어야 하고, `SEND_TX=true`는 **본인이 만든 연습용 니모닉**으로만 쓰세요(데모 니모닉은 관문이 막습니다). 이 저장소 작성자·검수자는 `SEND_TX=true`로 실행하지 않습니다.

## 🏠 내 생활에서는 <a id="life"></a>

지갑 앱(TronLink 등)에서 전송이 실패하면 빨간 글씨로 짧은 영문 문구가 뜹니다. 사건 1·3·4·8처럼 전송 단계에서 나는 실패는 지갑 앱에도 비슷한 영문 문구로 뜹니다. 한국어로는 "주소가 올바르지 않습니다", "계정이 활성화되지 않았습니다", "거래 실패", "잔고 부족"처럼 번역돼 보이기도 합니다(앱·버전마다 표기가 달라 실제 화면과 다를 수 있습니다 — 확인 필요). 반면 사건 6·7·9는 조회나 권한 확인이라 전송 실패 화면에 그대로 뜨는 문구가 아닙니다. 어느 쪽이든 문구를 지우지 말고 캡처해 두세요. 문구가 곧 원인입니다.

실패 문구를 캡처할 때 함께 적어 두면 원인 찾기가 훨씬 빨라집니다.

- 문구 전체(영문 그대로). 앱이 잘라서 보여 주면 "자세히"를 눌러 끝까지 봅니다.
- 어느 단계에서 났는지: 주소를 넣을 때 / 확인 화면에서 / 확인을 누른 뒤.
- 보내려던 토큰과 네트워크 이름, 그리고 그때 TRX 잔고.

실패했다고 자산이 사라진 것은 아닙니다. **사건 1~9 모두 잔고가 그대로입니다.** 사건 4는 이 레슨에서 리허설(`triggerConstantContract`)로만 확인하므로 수수료도 0입니다. 노드까지 실제로 간 것은 사건 3 하나뿐이고, 그것도 잔고 0인 새 키라서 검증에서 거부돼 수수료가 없습니다. 참고로 **실제로 전송한 뒤 REVERT 가 나면** 그때는 쓴 에너지·대역폭만큼 수수료를 내고 토큰은 그대로입니다(레슨 10 참고) — 이 레슨에서는 그 상황을 만들지 않습니다. 탐색기(레슨 7)에서 잔고를 직접 확인하세요.

**이런 요청이 오면 사기인가?**

| 상황 | 사기? | 이유 |

## 🛡️ 안전 규칙 카드 <a id="card"></a>

**규칙 12. 실패는 단서다. "고쳐 준다"는 사람은 사기다.**

**해야 할 것**
